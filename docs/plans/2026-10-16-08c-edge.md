# Plan 08c: the Edge runtime (polling, report, remote access, linkage)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** with `edge.enabled`, the gateway runs the saved Edge model as the ESP32's `edge_rt.c` does:
- it polls Modbus RTU and DL/T645 devices on either RS485 port, up to 5 Modbus TCP devices, the built-in IO and virtual (formula) points;
- it renders the report template periodically, on schedule and on change, and sends it through a port's socket;
- it answers remote access (Modbus RTU, Modbus TCP, rw_prot JSON) on that port's socket, mapped addresses included;
- it drives the outputs from the linkage events.

**Architecture:**
- **Boot load, one node at a time:** the model loads at boot through a new per-node visitor in `cfgmodel` (`cfg_edge_load`, sharing `cfg_edge_text`'s code). No cJSON tree of the whole model is ever built.
- **Pure logic in `edge_core`, host-tested:** batching, mapping, write encoding, change detection, linkage, schedule, MBAP reply matching.
- **Board side in `edge_rt.c`:** tasks, locks and I/O.
- **Reports reach a port's socket through a report slot in the bridge,** not through the serial MessageBuffer, which cannot carry a message larger than the bridge's 1.5 KB frame.
- **Remote access hooks into the bridge's receive path** of that port, before the 08a paths.

**Tech stack:** FreeRTOS, lwIP sockets, cJSON (in arena scopes), `jsonscan`, `edgecore`, `modbus`, `rwprot`. The bench peers run in Python on WSL and Windows.

## Global Constraints

- **The baseline is the ESP32's `edge_rt.c`, per §4 "copy, adapt"**:
  - a node that does not answer is marked failed, and polling goes on, with no retries;
  - values live in one cache guarded by one lock, held only while values are copied, never during I/O;
  - reports render one consistent snapshot, and on-change baselines move only after a report was sent.
- **Tasks (§6.1):**
  - `edge_bus[n]` (one per port that has devices), prio 5, 6 KB;
  - `edge_tcpN` (≤ 5, one per Modbus TCP device), prio 5, 5 KB;
  - `edge_ctl`, prio 6, 4 KB: IO, virtual and linkage, every 10 ms, never waiting on I/O;
  - `edge_rpt`, prio 4, 4 KB.
- **Locks (§6.4):** the order is the port's bus, then the Edge cache, then `store`, then FAL. Every wait has a timeout, and a timeout logs an error. The cache lock is never held across `serial_transact` or a Modbus TCP exchange.
- **Several ports (§6.4):**
  - an Edge device picks its bus with `uart` (1 or 2);
  - `edgeReport.channel` is 0 (MQTT), or 1 or 2 (that port's socket);
  - the IO slave (`io.modbusAddress`) answers on both ports.
- **Boot load (§9.4):**
  1. read the stored text into the Edge text buffer;
  2. run `cfg_load`'s rules (phases 1 and 2) one node at a time;
  3. build long-lived C structs and the FNV-1a index;
  4. compile the template on the heap;
  5. release the buffer.
- **Running out of memory** leaves Edge off with a status. It never yields a partial model.
- **The report buffer is at most 26 KB** (`edge_tmpl_size`). A larger one gives the status `TEMPLATE TOO LARGE` with reports off.
- **When `edgeReport` is saved,** the template is compiled against the running model's names. Over the limit, the save answers 4xx "The report template needs too many values for this gateway."
- **Configs are read once at boot.** Keep it simple, and run only the affected tests. Codex reviews before the PR.

## Review Focus

1. **A report larger than a bridge frame (1.5 KB), up to 26 KB, on any mode of the channel port:**
   - TCP client: one byte stream;
   - TCP server: every client;
   - UDP: one datagram, which IP fragments;
   - HTTP client: one request whose body is the report.

   Serial frames queued meanwhile keep their order and are never lost to the report. Covered by `test_bridge_core` (the slot rules) and the bench `bigreport`.
2. **A device that never answers on the bus** (10 nodes × 1 s):
   - linkage still follows within 0.5 s;
   - periodic reports keep their cadence;
   - the Modbus TCP device keeps being polled;
   - each dead node is tried once per round.

   Bench `dead`.
3. **A network request and Edge polling on the same bus:** each request gets its own reply, and no poll reply reaches the network client. Bench `contention`.
4. **Running out of memory at any allocation of the boot load:** Edge stays off with `NO MEMORY` and never runs a model with missing fields. `test_edge_core` `load_oom` covers it with a cJSON allocation-failure sweep through `json_alloc_failures`.
5. **A late Modbus TCP reply:** values stay with their own points (stale-transaction skip). Covered by `test_edge_core` `tcp_take` and the bench `late`.

## Rulings to approve

1. **Reports use a report slot in the bridge, not the serial MessageBuffer.**
   - `xMessageBufferReceive` leaves a message larger than the receive buffer at the head and returns 0 (`message_buffer.h`). One report over `FRAME_MAX` (1508 B) would block the port's queue for good.
   - **`bridge_send(port, data, len)`** offers the report: a pointer to Edge's report buffer, which lives on the heap for the whole run. It then waits on a per-port semaphore until the bridge has sent it to every connection, or lost them.
     - **It returns false at once** in these cases (`report_accept`, host-tested):
       - the port's bridge is not running;
       - it is a Modbus TCP client (a report is not a Modbus request);
       - it has no peer, unless the mode dials on demand.
     - **On-demand modes** are the HTTP client (one request per frame) and the TCP client with a short connection. A pending report opens their connection exactly as queued serial data does (Codex plan r1). The TCP client's "dial only on data" test becomes "a queued frame or a pending report".
     - While it waits, `edge_rpt` does not touch the buffer.
   - **The bridge** takes the slot in `take_frame` when no frame is in flight, ahead of the MessageBuffer. Serial frames keep their order behind it. The HTTP client's loop takes it through the same `take_frame`, not only from the MessageBuffer.
   - **Everything that touches the current frame uses `b->out` / `b->out_len`, `reply_tcp`'s `tx_finish` included** (Codex plan r1). A remote reply arriving while a report is half sent finishes the report from the same buffer first, never from `b->frame`, which would bring back 08b's TLS retry fault.
     - It sends the report as the current frame through the same paths: `tx_progress` per TCP connection, one `sendto` for UDP, one request for the HTTP client.
     - A report carries **no registration prefix**: it is the gateway's own message, not serial data. This differs from the ESP32, whose ring added the prefix to everything.
   - With this, the MessageBuffer keeps its single writer (`on_serial`). This is 08a ruling 2's "own writer path".
   - **`bufferOffline` keeps serial frames, not reports.** With no peer, a report is not sent and the baselines stay, so the change is reported again (as the ESP32 does when the channel is down). The ESP32's ring could also hold reports offline.
2. **Edge memory comes from the heap at boot, sized to the configuration, and is never freed.** This covers the device and point structs, the index, the snapshot arrays, the compiled template, the report buffer and the stacks of the Edge tasks (`xTaskCreate`).
   - §5.3 planned the model statically in AXI (about 20 KB) and the `edge_tcpN` stacks in AXI. AXI holds 473 KB of 512 KB today, heap included, so those no longer fit.
   - §6.1 put `edge_bus`, `edge_ctl` and `edge_rpt` in DTCM, 20 KB. DTCM holds 89 KB of the 120 KB budget, and Plans 09 and 10 still need `mqtt`, `mqtt_io`, `lte`, `cmux_rx` and `serial_hb` (about 20 KB).
   - On the heap, nothing is spent while Edge is off (the default), and only what the model needs while it is on.
   - **All or nothing (Codex plan r1).** `edge_start` reserves everything before anything runs:
     - the model, index, snapshots, template, report buffer, mutexes and semaphores;
     - each task's stack and TCB, with `pvPortMalloc`, for `xTaskCreateStatic`, which cannot fail.

     Only when every reservation succeeded does it set the bridge hook and create the tasks. Any failure frees what was reserved and leaves the status `NO MEMORY`, with no task and no hook.

     The sequence is a pure `edge_reserve(const edge_counts_t *, edge_alloc_t *)` with an injected allocator, host-tested with a failure at each allocation in turn.
   - **The worst case** is two buses, 5 TCP devices, 100 points and a 26 KB report: about 20 KB of `edge_bus`, `edge_ctl` and `edge_rpt` stacks, 25 KB of `edge_tcp` stacks, the model and a 26 KB report buffer. The model's size is measured in T2. The bench measures `heapMin` with both ports in TLS sessions as well.
   - §5.3 and §6.1 are updated.
3. **Remote access on the channel port, ahead of 08a's paths.** It is active with `remoteAccess` 1 and `channel` = n.
   - **Each request goes to Edge first:**
     - `remoteFormat` 1 (Modbus TCP): each MBAP frame from the connection's `mbtcp_acc_t`, the same accumulator as the Modbus gateway;
     - `remoteFormat` 0 (RTU): each RTU request, through a new `rtu_push` on the same accumulator;
     - `remoteFormat` 2 (rw_prot JSON): each segment or datagram.
   - **Edge answers only the units it exposes** (`edge_device_for_unit`). Anything else goes on down the 08a path unchanged: Modbus gateway, the IO slave on `io.modbusAddress`, polling, or the RS485 port.
     - So with the IO device mapped to another unit, the IO page's address still answers through 08a's IO slave on a Modbus gateway port.
     - In a transparent mode it goes on to RS485, as on the ESP32.
   - **A partial request is not held forever** (as the ESP32's `edge_flush_stale`). Bytes held in the accumulator that look like the start of an RTU or MBAP request, with no more bytes for 200 ms, go on down the 08a path as they are.
     - The bridge checks this on every pass (its select wakes at least every 10 ms).
     - `acc_stale(acc, now_us)` in `bridge_core` gives the rule. `mbtcp_acc_t` stamps the time of the **last** byte added (every push that adds bytes renews it), so silence is measured from the newest byte (Codex plan r2).
   - **Replies** go through `reply_tcp` (now `tx_finish`-safe) or `reply_udp`.
   - **HTTP client mode** has no remote access: requests come from the bus there, not the network.
   - **A remote read or write to a bus device blocks that bridge task in `serial_transact`,** as polling does (08a). Edge's own poll waits for the bus.
4. **Channel 0 (MQTT) before Plan 09:**
   - Edge runs (polling, linkage, the IO and virtual points);
   - reports and MQTT remote access are not sent;
   - the status reads `RUNNING n/m (MQTT: Plan 09)`;
   - one log line at boot says so.
5. **The clock:**
   - scheduled reports use `sysmgr_utc_ms` with `system.timezone` (`clock.c`), never newlib's `localtime`;
   - `sys_time` is a text "YYYY-MM-DD hh:mm:ss" in UTC, as on the reference unit (`clock_format`, zone 0);
   - **`sys_unix_time` is a number:** Unix seconds (the ESP32's `edge_rt.c:857`);
   - while the clock is not set, both give no value (the failure placeholder: 08b ruling 7, no made-up time leaves the device), and scheduled reports wait;
   - the pure `edge_sys_value(field, utc_ms, sn, mac, ver, &num, &text)` is host-tested for value and kind, with the clock set and unset.
6. **The boot load uses the web's Edge text buffer, handed over explicitly.**
   - `web_edge_buffer_for_boot(&cap)` is valid only before `webapi_start` (`configASSERT`). `edge_start` runs in `services_start`, before `webapi_start` (§6.3 step 6).
   - **`cfg_edge_load(env, text, len, on_device, on_node, ctx, err, errlen)`** runs phases 1 and 2 (non-strict, as `cfg_load`) through the same code as `cfg_edge_text`.
     - It hands each normalised device header and each normalised node, as cJSON, to the callbacks.
     - It emits no text, and what `cfg_edge_text` emits stays byte-identical (`test_edge_text`).
   - The callbacks copy what they need into C structs. They check `json_alloc_failures` first, then read fields.

## Architecture

### `cfgmodel`: `cfg_edge_load`

- **A static `edge_walk`** carries `cfg_edge_text`'s phases 1 and 2. Its new optional visitors are called with the normalised header `s` (after `put_any(name)`) and each normalised node `o` (after the IO and virtual fixes), before they are printed. With `emit` NULL, nothing is printed.
- **`cfg_edge_text`** calls `edge_walk` and then phase 3, unchanged.
- **`cfg_edge_load`** calls `edge_walk` with `strict` false and no emit. A visitor returning false stops the walk with `CFG_NO_MEMORY`.
- **Host tests:**
  - `test_edge_text` stays byte-identical;
  - `test_cfgmodel` gains `edge_load`:
    - visit order and counts;
    - the IO and virtual names fixed up;
    - a visitor's false is `NO_MEMORY`;
    - a model saved under the strict rules visits the same as `cfg_load` would have produced.

### `bridge` (08a), the report slot and the Edge hook

```c
/** A report to port n's peers as one frame, no registration prefix; waits until it is sent to every
 * connection or they are lost. False at once: bridge not running, no peer, Modbus TCP client mode. */
bool bridge_send(int port, const uint8_t *data, size_t len);
typedef size_t (*bridge_edge_fn)(const uint8_t *req, size_t len, uint8_t *reply, size_t max);
enum { BRIDGE_EDGE_RTU, BRIDGE_EDGE_MBAP, BRIDGE_EDGE_JSON };
/** Edge remote access on port n (before 08a's paths); 0 from fn: not Edge's, it goes on. */
void bridge_set_edge(int port, bridge_edge_fn fn, int framing);
```
- **The current frame becomes a pointer pair `b->out` / `b->out_len`:** `b->frame` for serial frames, or the slot for a report. `send_frames`, `udp` and `http_request` use it.
- **The slot** is `volatile const uint8_t *rpt; size_t rpt_len;`, taken under a critical section. The semaphore is given when the report is done or dropped.
- **`rtu_push(mbtcp_acc_t *, data, len, fn, ctx)`** (in `bridge_core`, host-tested) reassembles RTU requests with `mb_rtu_request_len`, as `mbtcp_push` does for MBAP. Bytes that are not a request go on as they are.

### `components/services/edge_rt.{h,c}` (board)

- **`edge_start(void)`** is called from `services_start` when `edge.enabled`, after the bridges and before `webapi_start`.
  - It loads the model: the web buffer and `store_edge_text`, then `cfg_edge_load` with the visitors writing into the heap structs, the index and formula references, then the `edgeReport` and `edgeLinkage` small configs.
  - It compiles the template, wires remote access, and creates the tasks.
- **Polling:**
  - `serial_transact(dev->uart, …)` for RTU and DL/T645;
  - a Modbus TCP exchange on `svc_net` sockets (`net_tcp_connect`, then `conn_send_all` and `conn_recv` with `edge_tcp_take`) under the device's own mutex;
  - IO through `iomgr_*`, with the AI encoded as float32 ABCD in mA as the IO map does;
  - virtual points through `edge_formula_eval`.
- **Remote access:**
  - Modbus through `mb_serve` over an `mb_map_t` whose callbacks use `edge_point_at` and the cache lock;
  - rw_prot JSON through `rwprot_handle`;
  - writes through `edge_write_req`, then `serial_transact` or the Modbus TCP exchange, checked with `edge_write_echo_ok`, then a read-back poll.
- **Report:** `edge_tmpl_render` under the cache lock, then `bridge_send(channel)` without the lock. On success the snapshot becomes the baselines.
- **Status for `/api/status` `edge.state`:**
  - `NOT RUNNING` (off);
  - `NO MEMORY`;
  - `TEMPLATE TOO LARGE`;
  - `RUNNING ok/total`, with the MQTT note of ruling 4.

  `Status.tsx` already shows `edge.state`.
- **The save check:** `edge_template_fits(const char *tmpl)` compiles the template against the running index (read-only after boot), on the heap, and frees it. `api.c` calls it before saving `edgeReport`. With Edge not running, the save goes through and the boot decides.

## Bench (`test/bench/edge_check.py`)

The ESP32's `test_edge.py`, without MQTT. Set-up:
- **The RS485 loop:** UART1 is the Edge bus. Port2 is a TCP server, and the PC (WSL) connects to it as the **bus slave**: it answers Modbus RTU unit 5 (FC1/3/5/6/15/16) and a DL/T645 meter on the bytes UART1's requests put on UART2.
  - Node timeouts are 500 ms, enough for RS485, port2's `packetInterval`, the LAN and the PC.
- **A Modbus TCP device** on Windows: `win_peer.py tcpserver modbus=1`, extended with FC5/6/16 echoes and `late=1`, a reply delayed past the timeout once.
- **Reports and remote access** use port1's socket: `channel` 1, TCP server on 23, the PC as the client.
- **The IO cases** use the DO state, readable without wiring. A DI case runs only on the board with the DO-DI pair wired, and the run asks for that wiring before it starts. AI values are not checked: this board has no Vref.

Cases:
1. **`basic`:**
   - a periodic report holding:
     - Modbus RTU (scaled, int16, float32, a coil);
     - DL/T645;
     - Modbus TCP;
     - IO (DO1);
     - virtual (a sum);
   - status `RUNNING n/n`;
   - batch reads, checked by the slave's request log: one FC3 for registers 10..13;
   - template constants kept, and `sys_sn`, `sys_mac` filled;
   - `sys_time` is the placeholder while the clock is unset.
2. **`change`:** an on-change report comes before the next periodic one; linkage (t ≥ 50 closes DO2, read through `/api/io`) and its log line.
3. **`schedule`:** the clock is set to hh:mm:50, and a report comes at the minute.
4. **`remote`, over port1's socket:**
   - rw_prot read, and writes (register, coil, DO), with DL/T645 refused;
   - the write reached the slave;
   - Modbus RTU on mapped slave 10, register 100;
   - an unmapped point stays at its own register;
   - with `remoteWrite` off: illegal function;
   - the virtual device at slave 200 (FC4 only);
   - the IO device mapped to 120;
   - a DL/T645 point mapped to holding register 50;
   - FC16 to a float32 point, and FC6 on half of one refused;
   - FC15 across a missing coil gives exception 2, with nothing changed;
   - a never-answering point gives exception 0x0B;
   - other JSON goes on to RS485, and Edge's requests never reach RS485.
5. **`split`:** MBAP and RTU requests split across segments, and two joined in one segment, each answered.
6. **`contention`:** 20 network Modbus requests to the bus slave through port1 (a Modbus gateway on the other unit) while Edge polls. Every request gets its own reply, no poll reply leaks to the client, and Edge keeps every point.
7. **`dead`:** 10 nodes of a device that never answers (1 s each):
   - linkage follows within 0.5 s;
   - periodic reports keep a 2 s cadence;
   - dead nodes show the placeholder;
   - the TCP device keeps being polled;
   - each dead node is asked once per round (the slave's log).
8. **`late`:** the Modbus TCP device answers one request late. The values stay with their own points.
9. **`shortreport`:** a TCP client with a short connection, no serial traffic at all; an on-change report dials and arrives, and the connection closes after the idle time.
10. **`partial`:** on the channel port, 3 bytes that start an RTU request, then silence; after about 200 ms they reach RS485 (the bus slave's log) and nothing is held.
11. **`bigreport`:** a template rendering about 6 KB:
   - over TCP, the whole report arrives as one byte stream, and serial frames from the bus queued in between arrive whole and in order after it;
   - a client that reads slowly sends a remote request while the report is half sent: the report arrives whole, then the reply (`reply_tcp`'s `tx_finish` on `b->out`);
   - over UDP, one datagram of the same size;
   - the 26 KB limit: saving a template that needs more is refused with the message, and the stored one is unchanged.
12. **`memory`:** with the largest model (100 points, 64 devices' worth of headers, 5 TCP devices, both buses) and both ports in TLS sessions: `heapMin`, the Edge allocations (boot log), and the free stack of every Edge task, all recorded.

Regressions: `bridge_check.py tcpserver modbus mbclient tcpclient udp http` and `tls_check.py tcpclient https`.

## Bench findings

**Firmware:**
- **newlib-nano's printf has no `%f`/`%g`** unless it is linked with `-u _printf_float`.
  - Every number in a report rendered empty (`edge_format`), so every report failed to render.

- **The largest model needs 9 Edge tasks** (two buses, 5 Modbus TCP devices, `edge_ctl`, `edge_rpt`), but `EDGE_MAX_TASKS` was 8. Edge stayed off with `NO MEMORY`.
  - Fixed. `test_edge_core` reserves 9 tasks (RED, then GREEN).
  - The start now logs which step failed.

**Bench:**
- **The bench upload** read UART7 for its whole window (up to 423 s). It now returns once the new app is up: about 55 s, of which 50 s is the transfer at 115 200 baud.
- **Report cadence** is counted as reports over the span, not as gaps between TCP segments. TCP split one report in two, and joined two in one.
- **The bench's clients use `TCP_NODELAY`.** With Nagle, the PC held the second piece of a split request until lwIP's delayed ACK, past the 200 ms partial-request rule (the ESP32's). A real master that splits a request with gaps over 200 ms is not answered by Edge, as on the ESP32.
- **The schedule:** the minute in which the clock is set is due at once (the ESP32's `schedule_due`), and the next report comes at :00.
- **`bigreport`** is about 3.2 KB: templates are at most 2048 characters (the schema), so 70 `sys_sn` slots make it. That is over twice the bridge's 1.5 KB frame. The 26 KB limit is checked by the save refusal.

## Code review round 1 (NOT APPROVED), and the fixes

The user's ruling, given during the review: **the device polling interval is the rest after each block (Modbus) or point (DL/T645)**, before the device's next one. The ESP32 waited it between whole rounds. A read-back after a remote write reads the whole device at once. `edge_step` and its test; the bench `basic` checks the gaps between a device's requests. Spec §6.4 is updated.

1. **An unreadable model ran as an empty one.** `store_edge_text` gives 0 only when the edge DB cannot be read (with no model saved it gives the default `[]`). Edge now stays off with `MODEL UNREADABLE` (§9.1).
2. **Out of memory in the template was taken for a bad template.**
   - `edge_tmpl_check` counts cJSON's failed allocations. A NULL from compiling a valid object is no memory.
   - The boot gives `NO MEMORY`, and the save answers 500 and keeps the stored config.
   - `test_edge_core` sweeps cJSON's and edgecore's allocations.
3. **A read ending at register 65536 wrapped to 0.** `edge_batches` now counts in 32 bits; `test_edge_core` `batch_top` covers it.
4. **RTU framing on a Modbus gateway port.** Each client now has its own Edge accumulator, taken from Edge's reservation (16 per port, about 4.4 KB, only with remote access on a socket). Edge's requests are cut out first, and the rest goes on to the gateway's own accumulator. Bench `gwrtu`.
5. **`bigreport` did not prove a half-sent report.** The client now stops reading for 7 s, then sends the request. The reply waited for 9475 report bytes, more than lwIP's send buffer and the PC's receive buffer hold together (8144). So the bridge held a report half sent, and it went out whole before the reply.
