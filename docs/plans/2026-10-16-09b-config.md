# Plan 09b: the config pipeline (defaults in FlashDB, plain saves, checks at boot, rules in the UI)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the user's direction of 2026-10-16:
- the web UI validates every config and sends it whole;
- the gateway only stores it: it checks authentication, the name, the size, the JSON syntax and the write;
- the boot loader checks every saved config before anything uses it. A config that fails stops what depends on it; the user fixes it, or restores the defaults with Reload;
- FlashDB is created with the defaults, from the one table they live in, and a factory reset rebuilds it with `fdb_kv_set_default`.

**Architecture:**
- **`store`** gets a FlashDB default KV table built from `cfgmodel`'s defaults. Its save path becomes a syntax check and a write: no merge, no normalisation, no rules. `edgeDevices` is split into 8 KB records by byte, behind the same generation and manifest.
- **The boot loader** (`store_init`, then each service's start) runs `cfgmodel`'s checks, strict for Edge. It records a state per config, and every service asks for that state before it starts.
- **The UI** carries every rule in one TypeScript module, `rules.ts`. Shared JSON fixtures run through both `rules.ts` and the C loader, and both must give the same verdict.

**Tech stack:** C (FlashDB 2.2.0, cJSON, `jsonscan`), TypeScript (React UI, `node --test` on `tsc` output), Python bench.

**Spec:** [2026-10-14-stm32-firmware-design.md](../specs/2026-10-14-stm32-firmware-design.md):
- §9.1: FlashDB (defaults, factory reset, validation at boot);
- §9.3: limits of the small configs;
- §9.4: saving `edgeDevices`;
- §10.3: the STM32 web UI;
- §11.4: the Reload button.

**Decisions:** asked of Codex, `stm32/docs/review/codex-gpt-6-astra-config-pipeline-design-2026-10-16.md` (D1–D8).

**Roadmap:** a new row 09b, between 09 (MQTT) and 10 (LTE). 09c (RAM: the static arena and the 48 KB Edge buffer gone, small buffers, streaming syntax check) follows, then the node limit is decided from 09c's measurements.

## Global Constraints

- **Limits:**
  - a small config's body is at most **10 240 bytes**, and `edgeDevices` at most **49 152 bytes**, NUL not counted;
  - an over-long body gets 413, and the stored config is kept.
- **A save checks only:**
  - authentication;
  - the name: 404 for an unknown one;
  - the size;
  - the JSON syntax, by `jsonscan` (RFC 8259, depth ≤ 32): 400 `The request body is not valid JSON.`;
  - the root type: an object for `network`, `port1`, `port2`, `mqtt`, `system`, `io`, `edge` and `edgeReport`; an array for `mqttPublish`, `mqttSubscribe`, `edgeDevices` and `edgeLinkage`. Otherwise 400 `The settings must be a JSON object.` or `… a JSON array.`;
  - the write: 500 on a flash error.

  There is no merge: the body replaces the whole config, and is stored byte for byte as sent.
- **GET returns what was stored, byte for byte.** The runtime uses the copy that the loader checked at boot.
- **Configs are read once, at boot.** Nothing is reconfigured live (spec §9.1).
- **Edge:** every record is written first, then the manifest; the manifest is the commit point (spec §9.4, kept as is).
- **No rescue mode,** no automatic switch to another admin config, no pending state, no rollback. When the web cannot be reached, the Reload button resets the configs.
- **Factory reset ≠ firmware restore.** Restoring the firmware stays the bootloader's job (spec §11.2).
- **Keep it simple, run only the affected tests, TDD.** No FlashDB patching beyond the recorded patch. Codex reviews before the PR.

## Review Focus

1. **A config saved by the previous firmware** (normalised, every field filled; `edgeDevices` cut by byte into 8 KB records through `s_chunk`). It must load unchanged; nothing asks the user to wipe. Pinned in T3 by a `test_store` case on a flash image written by the **writer of revision `850bdc6`** (main before 09b): `tools/pre09b_image.sh` checks that revision out into a temporary worktree, builds its `store` with a small host writer, and saves a set of configs and a 100-point model. The case checks that GET returns the same bytes as before the upgrade, and that the runtime is equivalent: each `store_get` during the boot equals `cfg_load` of the old text, and Edge's model loads with the same devices and points.
2. **A key the new firmware adds, missing from an old config.** It is an upgrade, not an error: the loader fills it with its default and the service runs. A wrong value in a present key is an error. Pinned in T3 by a `test_cfgmodel` case: a missing key loads and is filled; the same key with a bad value fails.
3. **A power cut during a factory reset** (three databases, not atomic). After the next boot, every config is either the default or the old saved one, never torn. If some are old, the user presses Reload again; nothing rolls back on its own. Pinned in T1 by `test_store`'s power-cut matrix over `store_factory_reset`.
4. **Out of memory, or a read error, at boot,** as distinct from a wrong config. The status says `NO MEMORY` or `UNREADABLE`, not `INVALID`, and no service starts half-loaded (Edge in particular). Pinned in T3 by a `test_store` case with failing allocations during `store_init`, and by `test_edge_core`'s existing all-or-nothing reserve.
5. **The Reload button and the safe outputs when `network`, `system` or `io` is invalid, or the cfg DB is unreadable.** Reload is sampled, and the DOs are held off on every path (`/api/io`, Modbus IO control, linkage), whatever the configs say. Pinned in T3 on the board: boot with `io` invalid, then a press of Reload through a new console bench command (`R <ms>`), which feeds "pressed" into the same 10 ms sampler in the `io` task for that long. The DOs read off meanwhile.

## Rulings to approve

1. **One source of defaults.**
   - `store` builds a `struct fdb_default_kv_node` table once, before `fdb_kvdb_init`, from `cfgdef_t.defaults`: one entry per small config, plus `edgeDevices` = `[]` with no manifest.
   - The table and its strings are static for the whole run, because FlashDB keeps the pointer.
   - A new DB (the first mount, or after a format) is written with these values.
   - A key missing from an older DB (a config a newer firmware added) is read from the same table at boot, and is not written.
2. **Factory reset** (`store_factory_reset`, from Reload and `POST /api/factory-reset`):
   1. it blocks every later write until the restart: configs, certificates, `edgeDevices`, and the DO state of `keepOutputs`;
   2. it calls `fdb_kv_set_default` on `cfg`, `edge` and `cert`;
   3. it reads every default back. FlashDB 2.2.0 ignores `create_kv_blob`'s result in `fdb_kv_set_default` (`fdb_kvdb.c:1435`), so only the read-back proves the reset;
   4. it restarts the gateway.

   It reports `factory settings restored` or `factory reset incomplete`, and restarts either way. The three DBs are not atomic together: after a power cut, the user presses Reload again.

   **Only a mounted DB is reset.** A DB that did not mount (ruling 10), or a flash that the FAL has locked read-only after a read error (spec §9.1, kept as is), is left alone; the reset reports `incomplete` and restarts, and the next boot tries again.
3. **The save path** is a plain store (Global Constraints).
   - `store_set_text` no longer calls `cfg_validate_text` or `listen_check`, and no longer parses.
   - `store_edge_save` checks the syntax and the root type over the whole body. It cuts the body into 8 KB records by byte, even in the middle of a UTF-8 sequence, then writes the generation and the manifest as before.
   - `edgeReport`'s save-time template check goes. It moves to the UI, and to the boot's `TEMPLATE TOO LARGE` (spec §9.4, kept: **only the reports** go off, Edge runs; an `edgeReport` that fails the loader's check stops Edge, ruling 5).
4. **The boot loader decides** (Codex D2, D7).
   - `store_init` loads each small config. A present key with a wrong value makes the config **invalid**: `cfg_load` reports it, and never corrects it. Missing keys are filled from the defaults.
   - `store` records a state per config: `STORE_CFG_OK`, `STORE_CFG_INVALID` (with the first error, as `cfgmodel` words it), `STORE_CFG_NO_MEMORY` or `STORE_CFG_UNREADABLE`.
   - **The stored copy and the runtime copy are apart.**
     - The cache holds the **raw bytes** as stored; `GET` (`store_get_json`) returns them, for an `INVALID` config too, so the UI can show and fix it. Filling a new key never changes them.
     - `store_get(name)` is the loader's: it parses the cached bytes, runs `cfg_load` (keys filled), and returns NULL unless the state is OK. It works only **during the boot**; after `store_boot_done()` (called once every service has started) it returns NULL. A save during the run therefore never changes this boot's runtime or its states.
     - Readers after the boot (`/api/status`'s `enabled` flags) use what each service recorded at its start, or `store_cfg_state`.
   - `store_cfg_state(name, err, len)` gives the state of this boot's check; a later save does not change it.
   - The cache is still the 20 KB pool, now of raw text: a save whose bytes do not fit the pool gets 413 `The settings do not fit in the gateway's memory.` (a size check).
   - Edge's model is loaded **strict** at boot (all three passes), because nothing checks it at save any more. A model saved by the previous firmware passed the strict check when it was saved, so it passes again.
5. **What stops when a config fails** (Codex D2, network and system included):

   | Failed config | What does not start |
   |---|---|
   | `network`, `system` (or the cfg DB unreadable, ruling 10) | every service: the network, the web, serial, bridges, MQTT, Edge, `sysmgr`'s SNTP and timers. `iomgr` runs in its safe mode (ruling 6); the console logs the failure |
   | `port<n>` | serial port n and `bridge[n]`; MQTT topics and Edge devices bound to port n stay idle. `serial_write`, `serial_subscribe` and `serial_transact` on a port that was never started return −1, so MQTT and Edge never reach an uninitialised driver |
   | `io` | `iomgr`'s DI/DO/AI service: safe mode (ruling 6); Edge's IO points are invalid |
   | `mqtt`, `mqttPublish`, `mqttSubscribe` | MQTT, with `mqtt.state` `CONFIG INVALID` |
   | `edge`, `edgeDevices`, `edgeReport`, `edgeLinkage` | Edge, with `edge.state` `CONFIG INVALID` (or `MODEL INVALID` for `edgeDevices`) |

   `/api/status` gains `configErrors: [{name, state, error}]` whenever the web runs. Each failure is also logged as an error, so it reaches the persistent log and the console.
6. **`iomgr`'s safe mode:** when `network`, `system` or `io` has failed, or the cfg DB is unreadable, `iomgr` starts without them.
   - The DOs are off and **held** off: every write is refused, from `/api/io` (409 `The IO is off: its settings are invalid.`), Modbus IO control (`io_mb_remote` answers exception 4) and linkage. No `keepOutputs` restore, no timers.
   - DI and AI are not served.
   - The Reload button is still sampled on the 10 ms tick, and the watchdog still runs.
7. **Listen ports** are checked at boot in a fixed order: the web (`webPort`, `websocketPort`), then `port1`, then `port2`.
   - A later service whose listen port is already taken does not listen.
   - Its state says `PORT IN USE (<port>)`, and the error is logged.
   - No port is changed automatically. `listen_check` moves from the save path to this boot check, and to the UI.
8. **The UI holds every rule** (Codex D7).
   - `stm32/web/src/lib/rules.ts` covers:
     - each field's type and range;
     - the cross rules: listen ports, a non-empty user name and password, `idleRestart` of 0 or at least 60, `allowedClients`;
     - every Edge model rule of `cfgmodel` passes 1–3 (spec §9.4 table);
     - the report template's worst-case size, by a port of `edge_tmpl_size` (`edgecore.c:407`) that follows the same rules (the template's own text, each slot by its point's type, escaping, the placeholder), against the C limit of **26 624 bytes**; its fixtures carry the model.
   - Pages call it before saving and send the whole config.
   - No code generation. The cross test (T4) keeps the two sides together: shared fixtures under `stm32/firmware/test/fixtures/config/`, run by `test_cfgmodel` and by `node --test`, with the same valid/invalid verdict for each.
9. **Certificates** keep their PEM and mbedTLS checks at upload (Codex D8). That is security material, not a config. 09c moves their 12 KB buffer to the heap, and wipes the key before freeing it.
10. **A cfg DB that cannot be mounted** (a flash fault) counts as `STORE_CFG_UNREADABLE` for every config. Ruling 5 then applies: no service starts, `iomgr` is in its safe mode. The gateway no longer runs on defaults in this case.
    - `store_init` no longer returns before setting the states. It marks every DB that did not mount, and nothing later calls FlashDB on it.
    - Reload then resets only the DBs that did mount (ruling 2), reports `incomplete` and restarts. The FAL's read-only lock is not lifted.

## Architecture

### `components/store/`

- `store.c`:
  - the default table (ruling 1);
  - `store_set_text` and `store_edge_save` as plain stores (ruling 3);
  - the state per config (ruling 4);
  - `store_factory_reset` (ruling 2): write block, read-back, restart through a new port hook, `store_port_restart()`.
- `store.h`: `store_cfg_state_t`, `store_cfg_state()`, `store_cfg_errors()` (a list for `/api/status`).

### `components/cfgmodel/`

- `cfg_load` stays as the loader's check. It must fail on a wrong value, never correct it: a host test pins this for every field kind.
- `cfg_edge_load(..., strict = true)` at boot.
- `cfg_listen_ok` moves to the boot (`app_main.c`/`services.c`), in ruling 7's order.

### `app/app_main.c`, `components/services/services.c`, `components/iomgr/`, `components/webapi/`

- The start order is unchanged.
- Each start asks `store_cfg_state` first, per ruling 5. `iomgr_start` gains its safe mode (ruling 6).
- `api.c` adds `configErrors` to `/api/status`.

### `stm32/web/`

- `src/lib/rules.ts`, pure: `configErrors(name, value, all)`, `edgeModelErrors(devices, env)`, `templateSize(template, devices, report)` (bytes, as `edge_tmpl_size`).
- The pages use it, and save whole objects.
- `tests/unit/rules.test.ts`, plus `tsconfig.test.json` (CommonJS output to `.test-build/`). Run with `npm run test:unit`, which is `tsc -p tsconfig.test.json && node --test .test-build/tests/unit`.

### Fixtures

- `stm32/firmware/test/fixtures/config/*.json`: one file per case, `{ "name": …, "value": …, "valid": true|false }`.
  - Configs that depend on another one (listen ports) carry `"with": { "system": …, "port1": … }`.
  - Edge cases carry the whole model.
- The cases cover:
  - number bounds (min − 1, min, max, max + 1);
  - wrong types;
  - empty and over-long strings;
  - each cross rule;
  - each Edge rule of the spec §9.4 table.
