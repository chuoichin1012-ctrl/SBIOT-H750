# Plan 08b: TLS (mbedTLS 3.6 LTS) on the bridge, and the certificate check on upload

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** both ports' TCP client and HTTP client can run over TLS 1.2:
- `tlsVerify` 0, 1 or 2;
- SNI;
- the no-clock date rule.

Certificate uploads are parsed and reported (F20), and the clock reads 2020-01-01 00:00:00 plus the uptime until it is set.

**Architecture:**
- mbedTLS 3.6.7 is vendored in `third_party/mbedtls` with its own `tls_config.h`.
- `tls_core.c` holds the pure parts and is host-tested against the real library:
  - the date rule;
  - the return-code mapping;
  - the certificate check;
  - `gmtime_r`.
- `tlsconn.c` runs a session over the bridge's non-blocking lwIP socket. It is host-tested over a loopback socket against an mbedTLS server.
- `svc_net`'s `conn_t` routes `send`, `recv` and `pending` through the session when there is one, so `bridge.c` changes only where a connection opens and where it waits.

**Tech stack:** mbedTLS 3.6.7 LTS, lwIP 2.2.1 sockets, FreeRTOS, Mongoose 7.23. The bench peers are Python `ssl` (OpenSSL 3) on Windows.

**Spec:** [2026-10-14-stm32-firmware-design.md](../specs/2026-10-14-stm32-firmware-design.md):
- §7.3: TLS;
- §10.4: the clock;

- §5.3: the RAM and heap budget, and ITCM for the bignum core;
- §5.5: the allocators;
- §6.1: the stacks;
- §5.6: lwIP, and sends that never block.

**Roadmap:** row 08, the second of its three parts:

## Global Constraints

- **mbedTLS 3.6 LTS,** pinned in `third_party`. It is `mbedtls-3.6.7` (2026-07-07, the latest 3.6.x). The tarball `mbedtls-3.6.7.tar.bz2` has SHA-256 `a7e8bcbec0e6f761b4af24f25677626b35f762f68eef79c08677a363212d11f6`, which matches the GitHub release digest.
- `MBEDTLS_SSL_IN_CONTENT_LEN` is 16384 and `MBEDTLS_SSL_OUT_CONTENT_LEN` is 4096.
- `MBEDTLS_HAVE_TIME_DATE` is on, and its time function returns the system time.
- Entropy comes from the hardware RNG (`MBEDTLS_ENTROPY_HARDWARE_ALT`, through `board_rng`).
- Cipher suites:
  - ECDHE with AES-GCM or CHACHA20;
  - RSA with AES-GCM;
  - TLS 1.2 only.
- Kept from the ESP32:
  - TLS 1.2;
  - `tlsVerify` 0/1/2;
  - SNI;
  - a deadline for the handshake and for writes;
  - the certificate check on upload (F20).
- **Without a clock and with `tlsVerify` ≥ 1:**
  - only `MBEDTLS_X509_BADCERT_EXPIRED` and `_FUTURE` are cleared, with a warning;
  - the chain, the CA and the host name are always checked;
  - once the clock is set, every handshake checks the dates in full.
- With `tlsVerify` 0, an outgoing connection does not check the certificate (as on the ESP32).
- **Configs are read once at boot.** Certificates are read from `store` at each TLS connection, as on the ESP32, so a port uses a new certificate at its next connection. MQTT, in Plan 09, reads its certificates once at boot.
- **Keep it simple, and run only the affected tests.** Codex reviews the code before the PR. No FlashDB patches.

## Review Focus

1. **Decrypted bytes held inside mbedTLS.** A 16 KB record read 1500 bytes at a time leaves the rest in the SSL context, where `select()` cannot see it. The bridge must still deliver all of it at once.
   - `test_tlsconn` "pending" case;
   - bench case `pending`: 4 KB in one `send`, then silence.
2. **A handshake against a silent or slow peer.** The bridge task (prio 8) must wait in `lwip_select` and never spin, and it must give up at its deadline. Meanwhile IO keeps its pace.
   - `test_tlsconn` "deadline" case;
   - bench case `silent`, with the 08a load measures: ADC windows/s and the DO pulse.
3. **A TLS peer that stops reading.** Each `tx_progress` call makes one `mbedtls_ssl_write` attempt. After `WANT_WRITE` it retries with the same pointer and length, which mbedTLS requires, and it still drops the connection after 10 s without progress.
   - `test_tlsconn` "slow reader" case: 256 KB intact;
   - the existing `test_bridge_core` stall case.
4. **Stack and heap under RSA-2048.**
   - At least 1 KB of stack must be left in `bridge[n]` (6 KB) after a handshake and after HTTPS, and in `web` (8 KB) after an upload that checks the pair.
   - `heapMin` is recorded with both ports in TLS sessions.
   - Bench cases `tcpclient`, `https`, `certs` and `twoports`.
5. **The 2020 display time never reaches what depends on the clock.** That means TLS dates, the IO timers, the log's wall time and `/api/time`.
   - `test_clock`: `clock_boot_format`;
   - `test_tls_core`: `tls_port_time` reads 0 while the clock is unset;
   - bench case `expired`: refused only after `POST /api/time`.

## Rulings to approve

1. **The config file is `tls_config.h`, not `mbedtls_config.h`.**
   - `build_info.h` does `#include MBEDTLS_CONFIG_FILE`. A quoted name is searched first in the including file's own directory, `include/mbedtls/`, so `"mbedtls_config.h"` silently picks up the library's default config. This was seen in the prototype build.
   - §7.3's text names the file loosely; the spec is updated.
2. **No `MBEDTLS_PLATFORM_MEMORY`.** mbedTLS calls `calloc` and `free`, and those are already the `heap_5` wrapper (§5.5). `check_elf` already checks that the binary holds only one `malloc`. The intent of §5.5 is met with one setting fewer. The spec is updated.
3. **No `MBEDTLS_THREADING_C`.**
   - Each session owns all its contexts: its ssl context, config, DRBG, entropy, certificates and key.
   - This config has no shared mbedTLS state: no PSA, no session cache, and our own `gmtime_r`.
   - `board_rng` already has a mutex. Two bridge tasks and `web` can therefore run mbedTLS at the same time.
4. **The port functions** are what the prototype build left undefined (`arm-none-eabi-nm -u` over all 176 objects, without what they define themselves):
   - `mbedtls_hardware_poll`, on `board_rng`;
   - `mbedtls_platform_gmtime_r`, on `clock_from_unix`;
   - `tls_port_time`, which returns `sysmgr_utc_ms()/1000`, so 0 while the clock is unset.
   `mbedtls_ms_time` is defined too, since `MBEDTLS_PLATFORM_MS_TIME_ALT` is needed to compile at all, though nothing calls it.
5. **The host name is always given (CVE-2025-27809).** Since 3.6.3, a client that checks the server and never called `mbedtls_ssl_set_hostname` fails the handshake. `tls_open` therefore always passes the dialled host (`remoteHost`, `httpHost`), names and IP addresses alike, for every `tlsVerify`.
   - mbedTLS 3.6 matches an IP address against the iPAddress SAN entries, and a name against the dNSName entries and the CN.
   - **A known limit when dialling an IP address:** mbedTLS puts whatever `set_hostname` received into the SNI, so an IP literal goes out as SNI, which RFC 6066 does not allow (`ssl_write_hostname_ext`, 3.6.7; Codex plan r1). mbedTLS 3.6 has no switch that keeps the name check and drops only the SNI.
     - The identity check is never given up for this. `set_hostname(NULL)` would remove the name check, so it is not used.
     - OpenSSL, and so Python, nginx and Mosquitto, accept the literal and select their default certificate. A server that refuses an IP SNI has to be dialled by name.
     - Spec §7.3 records the limit.
     - The ESP32 had the same behaviour: its `set_hostname` received the IP too.
   - `test_tlsconn` covers both forms. The server records the SNI it received:
     - dialling `localhost` (SAN `DNS:localhost`) succeeds, with SNI "localhost";
     - dialling `127.0.0.1` (SAN `IP:127.0.0.1`) succeeds, with SNI "127.0.0.1";
     - a name or an address missing from the SAN fails.
   - The bench dials an IP (`tcpclient`, `wrongname`).
   - The ESP32 skipped an empty host. On the STM32 an empty host never gets this far, because the connect fails first.
6. **`restartNeeded` is true only for `scope=mqtt`,** as on the ESP32. A port reads its files at each connection, and `CertUpload.tsx` already words it so ("MQTT uses it after a restart"). Until now the STM32 answered true for every scope.
7. **The 2020 clock is a display only (the user's request).**
   - While the clock is unset, `/api/status` `system.time` and the console's status line show 2020-01-01 00:00:00 plus the uptime, through a new `sysmgr_display_time()`.
   - `/api/status` gains `system.clockSet`, and `Status.tsx`'s "Clock not set" hint tests it. The old `startsWith('1970')` test can never fire on the STM32. This is a one-line UI change.
   - `sysmgr_time_str()` and `sysmgr_utc_ms()` keep returning "" and 0. Everything that depends on the clock reads those: TLS, the IO timers, `store_port_wall_ms`, and the log's `[boot N +hh:mm:ss]`.
   - **Edge `sys_time` (08c) stays empty while the clock is unset,** as §10.4 says today, so no made-up time leaves the device in a report.
   - `POST /api/time` already refuses years before 2024 (`CLOCK_MIN_YEAR`), so the 2020 time cannot be set back in by mistake.
8. **The bignum core goes to ITCM** (§5.3). `bignum_core.c` (about 3 KB) goes in `.itcm_text`. ITCM now holds 13.6 KB of 63 KB.
9. **Vendored files:** `library/`, `include/` and `LICENSE` only.
   - They are built at `-O2` without `-Werror`, as lwIP and Mongoose are.
   - The prototype at `-Os` was 106 KB of text before `--gc-sections`.
   - The app slot is 1472 KB and the app image is 361 KB today.

### `components/services/tls_core.{h,c}` (pure, host-tested: `test_tls_core`)

```c
/** The no-clock rule (spec §7.3): with the clock unset, clears EXPIRED and FUTURE from *flags.
 * True when it cleared any (the caller logs the warning). Other flags are never touched. */
bool tls_dates_skip(uint32_t *flags, bool clock_set);
/** An mbedtls_ssl_read/_write result: n > 0 as is; WANT_READ/WANT_WRITE -> NET_AGAIN;
 * 0, PEER_CLOSE_NOTIFY, CONN_EOF -> 0 (closed); anything else -> NET_FAIL. */
int tls_ret(int r);

typedef struct {
    char subject[160];
    char valid_to[11];  // "YYYY-MM-DD", certificates only
    int expired;        // -1 unknown (no clock, or a key), 0, 1
    char key_type[16];  // keys only: mbedtls_pk_get_name ("RSA", "EC")
    int pair;           // -1 not checked (a CA, or the other half missing or unreadable), 0, 1
} cert_info_t;
/** F20: parses pem (len bytes; pem[len] must be '\0') as kind "ca"|"cert"|"key". For cert and key,
 * other (the stored other half, or NULL) is checked against it with mbedtls_pk_check_pair.
 * now_s is the clock's UTC seconds, 0 while unset. 0, or -1 when pem does not parse as that kind. */
int cert_check(const char *kind, const char *pem, size_t len, const char *other, int64_t now_s,
               int (*rng)(void *, unsigned char *, size_t), cert_info_t *out);
```

- `expired` compares `valid_to` with `now_s` through `clock_from_unix`. It does not use `mbedtls_x509_time_is_past`, which reads the clock through `mbedtls_time` and would leave the test depending on the time port.
- `mbedtls_platform_gmtime_r()` also lives here, on `clock_from_unix`, so the dates mbedTLS checks are host-tested.

### `components/services/tls_port.c` (board only)

- `tls_port_time()` returns `sysmgr_utc_ms() / 1000`.
- `mbedtls_ms_time()` returns `now_us() / 1000`.
- `mbedtls_hardware_poll()` calls `board_rng`. If the RNG fails it returns `MBEDTLS_ERR_ENTROPY_SOURCE_FAILED`, and the DRBG seeding then fails, so the session is refused.
- `tls_port_rng()` is an `f_rng` on `board_rng`, for `cert_check` in `web`.

### `components/services/tlsconn.{h,c}` (host-tested over loopback: `test_tlsconn`)

```c
typedef struct tls_conn tls_conn_t;
/** TLS 1.2 client on fd (connected, non-blocking; the caller keeps owning it). Certificates from
 * store_cert_get(scope, "ca"|"cert"|"key") per verify (0 none, 1 CA, 2 CA plus our cert and key).
 * host: the dialled name or address, always set (SNI and name check). The handshake waits in
 * lwip_select for what mbedTLS wants, until timeout_ms. NULL on any failure, logged. */
tls_conn_t *tls_open(int fd, const char *scope, const char *host, int verify, uint32_t timeout_ms);
/** One mbedtls_ssl_write attempt: >0, NET_AGAIN, NET_FAIL (tls_ret). After NET_AGAIN the caller
 * must call again with the same data (tx_progress does: frame + off, len - off). */
int tls_send_some(tls_conn_t *t, const uint8_t *data, size_t len);
/** One mbedtls_ssl_read: >0, 0 closed, NET_AGAIN, NET_FAIL. */
int tls_recv(tls_conn_t *t, uint8_t *buf, size_t max);
/** mbedtls_ssl_check_pending: bytes or a record already inside mbedTLS (select cannot see them). */
bool tls_pending(tls_conn_t *t);
/** close_notify (one try, non-blocking), then frees everything. NULL is fine. */
void tls_close(tls_conn_t *t);
```

- **Each session owns:** the ssl context, its config, a CTR-DRBG seeded from the hardware entropy, the CA, our certificate and our key.
- **`tlsVerify` 1:**
  - `MBEDTLS_SSL_VERIFY_REQUIRED` on the uploaded CA;
  - a verify callback that applies `tls_dates_skip(flags, sysmgr_clock_set())` at each depth and logs "certificate dates not checked: the clock is not set yet" once per handshake.
- **`tlsVerify` 2** adds our certificate and key through `mbedtls_ssl_conf_own_cert`.
- **A missing file** fails before the handshake, with the ESP32's messages:
  - "server verification needs a CA certificate; upload one";
  - "mutual TLS needs a client certificate and key; upload both".
- **The handshake loop:**
  - `WANT_READ` waits in `lwip_select` for read on the fd; `WANT_WRITE` waits for write;
  - each wait is given the time left to the deadline, so the task never spins;
  - when the deadline passes the result is `MBEDTLS_ERR_SSL_TIMEOUT`.
- **A failure** logs the mbedTLS error text, and "certificate rejected (flags 0x%lx)" when the verify result is set. Both lines are rate-limited like the connect failure: at most once a minute per port.
- **The BIO** is `lwip_send` and `lwip_recv` with `MSG_DONTWAIT`.
  - `EWOULDBLOCK` and `EAGAIN` become `WANT_WRITE` or `WANT_READ`, and so do `ENOMEM` and `ENOBUFS` (`net_classify`, §5.6).
  - Anything else becomes `MBEDTLS_ERR_NET_SEND_FAILED` or `_RECV_FAILED`.
  - In the host test the `lwip_*` names map to POSIX (`test/host/tls_shim.h`).
- **After the first handshake of each boot,** a log line reads "stack headroom after the TLS handshake: N bytes" (`uxTaskGetStackHighWaterMark` × 4). The bench reads it, as on the ESP32.

### `svc_net` and `bridge.c`

- **`conn_t.tls`** becomes a `tls_conn_t *`.
  - `conn_send_some` and `conn_recv` go through `tls_send_some` and `tls_recv` when it is set.
  - `conn_close` calls `tls_close` before `closesocket`.
- **New:** `bool conn_pending(const conn_t *c)`, which is `c->tls && tls_pending(c->tls)`.
- **`bridge_start`:** the "TLS UNAVAILABLE" refusal goes.
- **TCP client:**
  - after `net_tcp_connect`, with `C.tls` set, it calls `tls_open(fd, "port<n>", C.host, C.tls_verify, 10000)`;
  - if that fails, the socket is closed and the retry follows `reconnectInterval`, as a failed connect does;
  - the state stays "CONNECTING" until the session is up;
  - short connections and the Modbus TCP gateway use the same path.
- **HTTP client:** `tls_open(fd, "port<n>", C.http_host, C.tls_verify, httpTimeout × 1000)`. After the first HTTPS request of the boot, a log line reads "stack headroom after HTTPS: N bytes".
- **`wait()`:**
  - a client with `conn_pending` sets the timeout to 0;
  - after `lwip_select`, such a client's fd is added to `rd`, so `read_clients` reads it on this pass;
  - **`wait()`'s result counts them** (Codex plan r1). The bridge calls `read_clients` only when `wait()` returns more than 0, and `lwip_select` returns 0 when the socket is silent and the bytes are inside mbedTLS. The result is `wait_ready(selected, pending)` from `bridge_core`: `max(selected, 0)` plus the pending clients whose fd `select` did not set. Without that count the bytes would stay stuck, and the 0 timeout would spin;
  - the 8-read bound and the round-robin start stay as they are.
- **`tx_progress` and `conn_send_all`** are unchanged. On `NET_AGAIN` both already call again with the same remaining data, which is what `mbedtls_ssl_write` requires. A comment at `tx_progress` says so, so that a later change keeps it.

### `web.c` (F20)

`upload_complete`, cert branch:
1. `web_pem_check` stays as the first gate, with the same 400 messages.
2. `s_edge_body[s->got] = '\0'`. The buffer is `WEB_EDGE_MAX + 1` and `WEB_CERT_MAX` < `WEB_EDGE_MAX`.
3. For `cert` and `key`, `other = store_cert_get(scope, other kind)`.
4. `cert_check(kind, body, got, other, sysmgr_utc_ms() / 1000, tls_port_rng, &info)`. A failure gives 400 with the same message as `web_pem_check`.
5. `store_cert_set`, then reply with:
   - `subject` and `validTo` (certificates);
   - `expired`, only when it is known;
   - `keyType` (keys);
   - `pairMatches`, only when the pair was checked;
   - `restartNeeded`, which is `scope == "mqtt"`.

   A pair that does not match is reported but still stored, as on the ESP32.
6. **The bench line:** after the first upload of each boot that checked a pair, a log line reads "stack headroom after the certificate check: N bytes".

## Bench (`test/bench/tls_check.py`)

The TLS section of the ESP32's `test_bridge.py`, against Windows peers. UART1 is the TLS port and UART2 is the device side (E/F), as in 08a.

- **The PKI** is made in WSL with `openssl` 3.0 and copied to `C:\Users\Public\sbiot\tls\`:
  - a CA;
  - a server certificate for `IP:192.168.0.10` (RSA-2048, valid 2 days) signed by that CA;
  - a server certificate from the same CA whose only SAN is `IP:192.168.0.99`;
  - a second CA, unrelated to the first, and a server certificate it signed;
  - a client certificate `CN=gateway` with its key.
- **`win_peer.py`** gains `tlsserver` and `https`.
  - `tlsserver` takes `port`, `cert`, `key` and an optional `clientca`.
  - It has these modes:
    - echo data (as `tcpserver`);
    - `send_hex` after the handshake;
    - `big=4096` (one `send` of 4 KB, then silence);
    - `silent=1` (accepts TCP and never answers the handshake).

Cases:
1. **`certs`:**
   - The CA upload reports its `subject` and `validTo`. `expired` is absent, since the clock is unset.
   - A damaged certificate is refused with 400.
   - A certificate sent as a key is refused with 400.
   - `restartNeeded` is false for `port1` and true for `mqtt`.
   - On `scope=port2`, which no TLS case uses, the client certificate is uploaded, then the wrong key: `pairMatches` is false. Then the right key: `pairMatches` is true, and `keyType` is RSA. `port1` therefore holds no key until `mutual`.
   - The `web` headroom is at least 1 KB.
2. **`tcpclient`:** `tls` 2, `tlsVerify` 1, with the CA.
   - serial → server, and server → serial;
   - the "certificate dates not checked" warning appears;
   - the `bridge1` headroom after the RSA-2048 handshake is at least 1 KB;
   - `/api/status` shows CONNECTED.
3. **`wrongca`:** the server's certificate is signed by the other CA.
   - The handshake is refused and "certificate rejected" is logged.
   - No data reaches the server. The port retries.
4. **`wrongname`:** the server's certificate is signed by the right CA, but its only SAN is `IP:192.168.0.99`, while the board dials 192.168.0.10.
   - The handshake is refused and the name flag (0x4) is logged.
5. **`pending`:** the server sends 4 KB in one `send`, then nothing. UART2 counts all 4096 bytes within 2 s.
6. **`mutual`:**
   - `tlsVerify` 2 against a server that requires a client certificate.
   - The case starts with only the client certificate on `port1`. The "mutual TLS needs a client certificate and key" line appears and nothing connects.
   - Then the key is uploaded, and at the next connection the server sees `CN=gateway` and the data flows.
   - There is no delete for certificates, so the run starts from `Z WIPE` (T5).
7. **`https`:** HTTP client, `tls` 2, `tlsVerify` 1, GET.
   - "OK-HTTPS" reaches UART2;
   - the headroom after HTTPS is at least 1 KB.
8. **`silent`:** the TCP client dials a `silent=1` server.
   - The handshake gives up within 10 s ± 1 s, and the port retries.
   - Over 30 s of handshakes failing in a loop (a wrong CA, `reconnectInterval` 1), the 08a load measures hold:
     - ADC windows/s within 5 % of idle (`adc_pace`, on the board's clock);
     - a 2000 ms DO pulse at 2000 ± 20 ms.
9. **`twoports`:** port1 is a TLS TCP client and port2 is an HTTPS client, with a request every second for 30 s.
   - Both work.

## Code review round 1 (NOT APPROVED), and the fixes

1. **A reply could interleave with a frame in flight.** A Modbus or polling reply went out through `conn_send_all` on a connection whose serial frame was half sent.
   - With plain TCP, the bytes mixed. With TLS, `mbedtls_ssl_write` got other data after `WANT_WRITE`, so the reply could be lost and the old frame sent twice.
   - **Fix:** `tx_finish` (`bridge_core`) sends the in-flight frame whole before anything else goes on that connection, within the reply's 2 s. Otherwise the connection is dropped. `reply_tcp` calls it.
   - `test_bridge_core`: one stream, the frame and then the reply; nothing in flight means nothing is sent; a peer that takes nothing is lost after 2 s.
   - Bench: `bridge_check.py tcpserver modbus mbclient`, and `tls_check.py tcpclient pending https`.
2. **`mbedtls_ssl_conf_own_cert`'s result was ignored.** It allocates: running out of memory there let `tlsVerify` 2 go on without our certificate.
   - **Fix:** the result is checked.
   - `test_tlsconn` `mutual_oom` fails each `calloc` of the client's thread in turn (6389 of them), against a server that would accept a session without a client certificate. It found exactly that one session before the fix, and none after.
