# Plan 09: MQTT (coreMQTT 2.3.1, the outbox, mqttgw)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the ESP32's MQTT gateway on coreMQTT, for both ports:
- publish modes 0/1 and custom mode;
- subscribe modes 0/1 with `+`/`#`;
- IO control;
- MQTT 3.1 and 3.1.1, clean session, keep-alive, authentication, LWT, TLS;
- `retryInterval` and `reconnectIfSilent`.

Delivery is exactly as spec §8 states for each kind of session, through an outbox with a state per message. Edge's channel 0 (reports and remote access over MQTT) comes alive.

**Architecture:**
- **coreMQTT 2.3.1** is vendored with a small, recorded MQTT 3.1 patch.
- **Pure, host-tested parts:**
  - `mqtt_transport` maps coreMQTT's transport contract onto `conn_t`, waiting in `lwip_select` so coreMQTT's internal loops never spin;
  - `mqtt_outbox` holds the messages in place, with their states, in SRAM2+3.
- **`mqttgw` on the board:**
  - one `mqtt` task owns coreMQTT;
  - one `mqtt_io` task moves frames between the serial ports, the outbox and Edge;
  - each side hands its data to bounded rings in SRAM4.

**Tech stack:** coreMQTT 2.3.1, mbedTLS 3.6.7 (`tlsconn`), lwIP sockets, FreeRTOS. On the bench: mosquitto 2.0.18 in WSL, and a Python relay on Windows with fault injection.

**Spec:** [2026-10-14-stm32-firmware-design.md](../specs/2026-10-14-stm32-firmware-design.md):
- §8: MQTT;
- §5.3: RAM (outbox 64 KB in SRAM2+3; the `mqtt_io` rings 2 × 12 KB in SRAM4; coreMQTT's buffers 2 × 4 KB on the heap);
- §6.1: tasks `mqtt` 6 KB at prio 5 and `mqtt_io` 4 KB at prio 5;
- §6.4: coreMQTT is called by `mqtt` only, the outbox mutex is never held over the transport, the lock order;
- §7.3: TLS;
- §10.4: no `WAITING FOR CLOCK`.

**Roadmap:** row 09, "coreMQTT 2.3.1 with the 3.1 patch, transport adapter, outbox with per-message states, mqttgw, retained messages after resubscribe".

## Global Constraints

- **coreMQTT v2.3.1,** pinned. Its release asset `coreMQTT-v2.3.1.zip` has SHA-256 `4bf0d8de9fbed4b35c5f149f7009b06946834ea3d8384b1d39e1c392f8316563` (the release carries no digest, so this one was taken on download). v5 is MQTT 5 and is out of scope.
- **The MQTT 3.1 patch:**
  - CONNECT carries `MQIsdp` at level 3;
  - in 3.1 the CONNACK has no Session Present, so a session is kept exactly when `cleanSession` is 0.
- **The transport's results** (spec §8 table):

  | From the connection | To coreMQTT |
  |---|---|
  | n > 0 | n |
  | nothing yet | 0 |
  | closed (0, close-notify) | −1 |
  | an error | −1 |

  A partial write returns the bytes written.
- **The outbox:**
  - the states are `QUEUED`, `WAIT_PUBACK`, `WAIT_PUBREC` and `WAIT_PUBCOMP`;
  - messages are resent only on reconnect;
  - a kept session resends PUBLISH with DUP and the old packet id, and coreMQTT resends PUBREL;
  - a new session sends the messages again as `QUEUED` with new packet ids;
  - it holds 64 KB; when full, a new message is dropped with a warning;
  - only `QUEUED` messages expire, after 1 hour;
  - with `bufferOffline`, messages queue while offline, QoS 0 included;
  - it never blocks a serial task.
- **Every subscription is made again after each connect.** Retained messages then come again and go to the bound port like any other message.
- **Behaviour kept from the ESP32:** everything listed in Goal, IO control, and the `NO CA CERTIFICATE` / `NO CLIENT CERTIFICATE` states. `WAITING FOR CLOCK` is gone.
- **Configs are read once at boot.** Keep it simple, and run only the affected tests. Codex reviews before the PR.

## Review Focus

1. **A broker that goes silent mid-packet, or a send window that stays full:**
   - the `mqtt` task waits in `lwip_select` and never spins;
   - lower-priority tasks keep running (`edge_rpt`, `syslog`, `idle`).

   Covered by `test_mqtt_transport` (CPU time while a peer is silent mid-packet) and the bench case `silent`.
2. **A disconnect at each QoS phase, for each version and `cleanSession`:**
   - a kept session never loses a message and never duplicates a QoS 2 message;
   - a new session never loses one, and may duplicate a payload.

   Covered by `test_mqtt_session` (the real coreMQTT against a scripted broker) and the bench `qos` matrix.
3. **More than 16 messages in flight, and a 26 KB Edge report:**
   - the outbox stops feeding coreMQTT while its 16-entry state table is full;
   - a large payload goes out straight from the outbox record.

   Covered by `test_mqtt_session` and the bench `edge`.
4. **An incoming PUBLISH larger than the 4 KB receive buffer, at QoS 0, 1 or 2:**
   - its payload is dropped with a warning;
   - its QoS exchange is still completed (PUBACK, or PUBREC then PUBCOMP), so the broker's in-flight window moves on;
   - the connection stays up, so resubscribing cannot start a reconnect storm.

   Covered by `test_mqtt_session` (QoS 1 and 2, then a normal message) and the bench `oversized` (mosquitto with `max_inflight_messages 1`).
5. **An empty client ID with MQTT 3.1, or with `cleanSession` 0:** one is derived (ruling 4), so the broker does not refuse it. Covered by `test_mqtt_wire` and the bench `connect`.

## Rulings to approve

1. **The coreMQTT patch lives in `third_party/patches/coremqtt-2.3.1-sbiot.patch`** and is applied in-tree, as the lwIP and FlashDB patches are. It covers MQTT 3.1 and oversized incoming messages (ruling 11).
   - It adds `bool mqtt31` to `MQTTConnectInfo_t`, false by default (3.1.1).
   - It changes four things:
     - the protocol name `MQIsdp`, level 3, and a Remaining Length 2 bytes longer;
     - in 3.1, the CONNACK's first byte (reserved) is not checked;
     - `sessionPresent = !cleanSession` before `handleSessionResumption`;
     - nothing at all for 3.1.1.
2. **The transport never returns 0 without waiting** (facts from `core_mqtt.c`):
   - `sendBuffer` calls `send` again with no pause until `MQTT_SEND_TIMEOUT_MS`;
   - `recvExact` does the same until `MQTT_RECV_POLLING_TIMEOUT_MS`.

   So on "nothing yet" the adapter first waits up to 10 ms in `lwip_select`, for writability or readability.
   - **Only the receive path** skips that wait, and only when `tls_pending` says bytes are already inside mbedTLS. A send that gets `NET_AGAIN` always waits for writability, whatever is held for reading (Codex plan r1).
   - **`select` can return at once.** Then two results in a row without progress also sleep one tick (`vTaskDelay(1)`), so the CPU is given up even then. `test_mqtt_transport` covers it with a wait that returns at once.
   - `core_mqtt_config.h` sets `MQTT_SEND_TIMEOUT_MS` 10000, `MQTT_RECV_POLLING_TIMEOUT_MS` 50, `MQTT_PINGRESP_TIMEOUT_MS` 10000, and logging to `syslog`.
3. **The outbox keeps every message in place, in a ring of records** in SRAM2+3 (64 KB).
   - `mqtt_io` and Edge only append, under the mutex. Only `mqtt` changes states and deletes.
   - A record never moves, so `mqtt` publishes from it without the mutex: `MQTT_Publish` sends the payload by I/O vector, with no copy.
   - Space is reclaimed from the head over deleted records, so a slow QoS 2 exchange can hold space behind it. That stays within the 64 KB and is the price of zero copies.
   - At most 16 messages are in flight (coreMQTT's state tables, `MQTT_InitStatefulQoS` with 16 per direction). `QUEUED` messages wait while 16 are in flight.
   - **A new session** (3.1.1 Session Present 0, or 3.1 with `cleanSession` 1) sends the `WAIT_*` messages again as `QUEUED`, with fresh packet ids, once `MQTT_Connect` has returned. coreMQTT has cleared its own records by then.
   - **One context for the whole run** (Codex plan r1). `MQTT_Init` resets the packet id counter, so it runs once, at start, with the two 16-entry QoS tables (`MQTT_InitStatefulQoS`). A reconnect only swaps the transport's connection and calls `MQTT_Connect`. The ids then never restart while messages wait for their acks.
   - **A PUBLISH that fails midway** (`MQTT_Publish` returns an error after coreMQTT reserved its id) still moves the record to `WAIT_PUBACK`/`WAIT_PUBREC` with that id: its bytes may have reached the broker.
     - A kept session resends it with DUP and the same id. The collision is accepted.
     - A new session sends it again with a new id. coreMQTT's records were cleared.

     `test_mqtt_session` covers a drop in the middle of a PUBLISH, with more messages queued behind it.
   - **A kept session** resends with `dup = true` and the old id; coreMQTT accepts the state collision for a DUP.
   - **Expiry** is 1 hour of uptime, not wall-clock time, since the clock may be unset.
4. **The client ID:**
   - empty: `SBIOT-<last 6 hex digits of the MAC>` (the ESP32's esp-mqtt derived one from the MAC);
   - with 3.1, longer than 23 characters: sent as given, and a refusal shows `REFUSED`, as any CONNACK refusal does.
5. **TLS** through `tlsconn` with scope `mqtt`.
   - The name for SNI and the certificate check is `sniHost` when `sni` is set and `sniHost` is not empty, otherwise `host`.
   - `sni` false cannot omit the name (08b ruling 5, CVE-2025-27809); it means "check against `host`".
   - Certificates are read at each connect, as for the ports. The `NO CA CERTIFICATE` / `NO CLIENT CERTIFICATE` states are decided at boot, and MQTT then stays off.
   - `restartNeeded` stays true for mqtt.
6. **IO control is Modbus RTU only** (`io_mb_remote` to `io.modbusAddress`). The ESP32 code does only that, though its docs mention JSON. The reply is published on every publish topic with `ioControl`.
7. **`reconnectIfSilent`** counts only incoming PUBLISH messages and connects, not PINGRESP, as on the ESP32.
8. **Two ports:**
   - a topic's `ports` bitmask binds it to UART1 (bit 0) and/or UART2 (bit 1);
   - custom mode reads the ports in `customModePorts`;
   - the up-ring is one MessageBuffer per port (6 KB each), keeping one writer per buffer;
   - the down-ring (broker → `mqtt_io`) is 12 KB, written by `mqtt` only.

   All three are in SRAM4.
9. **Listeners added while connected** (Codex plan r1). `mqttgw_add_listener` adds the entry under the mutex and notifies the `mqtt` task, which subscribes at once when connected. On every connect, everything is subscribed again. A pure `subs` list with a "subscribed in this session" flag per entry (`mqtt_subs.c`) decides what to send; `test_mqtt_outbox` covers adding after CONNECTED, with no reconnect.
10. **Edge's channel 0:**
   - reports go through `mqttgw_publish` into the outbox (a 26 KB report takes a large part of it; refused when it does not fit, and the baselines stay);
   - Edge's request topic is a listener whose callback runs in `mqtt_io` (it may wait on a device);
   - its reply goes back through the outbox on `replyTopic`;
   - the "MQTT: Plan 09" note goes;
   - `mqttgw_start` loads its config and listener table before `edge_start`, and the `mqtt` task subscribes every listener on each connect.
11. **Incoming messages over the 4 KB receive buffer** (Codex plan r1). coreMQTT 2.3.1 drops such a packet before its QoS handling, so a QoS 1/2 message would never be acknowledged, and the broker's in-flight window would stall.
    - **The patch:** for a dropped PUBLISH whose fixed header, topic and packet id fit in the buffer, coreMQTT runs the same `MQTT_UpdateStatePublish` and `sendPublishAcks` as `handleIncomingPublish` does. So a QoS 1 message gets its PUBACK, and a QoS 2 message its PUBREC, then PUBCOMP on PUBREL.
    - No event reaches the application: the payload is dropped with a warning, as the ESP32 did with messages over 4 KB.
    - When even the topic does not fit, the connection is closed, which is logged; this cannot happen with topics of at most 4 KB.
12. **`/api/status` `mqtt.state`:**
    - `NOT RUNNING` (off);
    - `CONNECTING`, `CONNECTED`, `REFUSED`;
    - `NO CA CERTIFICATE`, `NO CLIENT CERTIFICATE`;
    - `NO MEMORY`.

## Architecture

### `third_party/coremqtt/`

- The release zip's `source/` and `LICENSE` (MIT), plus a `README.md` with the source, SHA-256, files and patch, as the lwIP README does.
- `components/services/include/core_mqtt_config.h` holds ruling 2's values and `LogError`/`LogWarn`/`LogInfo` mapped to `SLOG_*` (Debug off).

### `components/services/mqtt_transport.{h,c}` (host-tested: `test_mqtt_transport`)

```c
typedef struct { int (*send)(void *c, const uint8_t *d, size_t n); int (*recv)(void *c, uint8_t *b, size_t n);
                 bool (*pending)(void *c); int (*wait)(void *c, bool write, uint32_t ms); void *conn; } mqtt_link_t;
int32_t mqtt_tx(NetworkContext_t *nc, const void *buf, size_t n);   // TransportSend_t
int32_t mqtt_rx(NetworkContext_t *nc, void *buf, size_t n);         // TransportRecv_t
```
- **Ops:** on the board they are `conn_send_some`, `conn_recv`, `conn_pending` and a `lwip_select` wait. In the host test they are POSIX sockets.
- **Results** follow the Global Constraints table: `NET_AGAIN` returns 0 only after one wait of up to 10 ms.

### `components/services/mqtt_outbox.{h,c}` (host-tested: `test_mqtt_outbox`)

```c
enum { OB_QUEUED, OB_WAIT_PUBACK, OB_WAIT_PUBREC, OB_WAIT_PUBCOMP };
typedef struct ob_msg { uint8_t state, qos; bool retain; uint16_t id, topic_len; uint32_t len, t_ms; /* topic, payload */ } ob_msg_t;
bool ob_push(ob_t *o, const char *topic, size_t tlen, const void *data, size_t len, int qos, bool retain, uint32_t now_ms);
ob_msg_t *ob_next_queued(ob_t *o, uint32_t now_ms);          // expires QUEUED > 1 h on the way
void ob_sent(ob_t *o, ob_msg_t *m, uint16_t id);              // QoS 0: deleted; 1: WAIT_PUBACK; 2: WAIT_PUBREC
void ob_ack(ob_t *o, uint16_t id, int type);                   // PUBACK / PUBREC -> WAIT_PUBCOMP / PUBCOMP
void ob_session(ob_t *o, bool kept);                          // after a connect: kept -> the resend list; new -> QUEUED
ob_msg_t *ob_next_resend(ob_t *o, ob_msg_t *after);           // WAIT_PUBACK / WAIT_PUBREC, in order
int ob_in_flight(const ob_t *o);
```
- The mutex is the caller's (`mqttgw`). The functions are pure, over a caller-provided region.

### `components/services/mqttgw.{h,c}` (board) and `mqtt_session` logic

- **The `mqtt` task:**
  1. connect: `net_tcp_connect`, then `tls_open` when TLS is on, then `MQTT_Connect` with the session rule. `MQTT_Init` and `MQTT_InitStatefulQoS(16, 16)` run once, at start;
  2. `ob_session(kept)`, the resends, every subscription and listener;
  3. loop:
     - feed `QUEUED` messages while fewer than 16 are in flight;
     - run `MQTT_ProcessLoop`; its event callback calls `ob_ack`, or pushes an incoming PUBLISH (topic and payload) onto the down-ring without waiting;
     - check `reconnectIfSilent`;
  4. on any error: close, then wait `retryInterval`.
- **The `mqtt_io` task:**
  - the up-rings: per topic, transparent or distribute (`mqtt_alias_match`), or custom mode (`mqtt_custom_parse`), then `ob_push`;
  - the down-ring:
    - Edge listeners;
    - IO control (`io_mb_remote`, the reply to the `ioControl` publish topics);
    - mode 0/1 to the bound ports with `serial_write`.
- **The serial subscribers** (one per bound port) only queue frames, in `serial_rx[n]`.
- **API:**
  - `mqttgw_start(sys)` before `edge_start`;
  - `mqttgw_status`;
  - `mqttgw_publish(topic, data, len, qos, retain)` for Edge;
  - `mqttgw_add_listener(topic, qos, fn)`.

### `test_mqtt_wire`, `test_mqtt_session` (host)

- **`test_mqtt_wire`:**
  - CONNECT byte for byte, 3.1 and 3.1.1: name, level, flags, Remaining Length, client ID, will, user and password;
  - a 3.1 CONNACK with a non-zero reserved byte is accepted, and `sessionPresent` is `!cleanSession`;
  - a 3.1.1 CONNACK with the Session Present bit.
- **`test_mqtt_session`:** the real coreMQTT and outbox against a scripted broker (a thread on a socketpair). One context serves several connections, as on the board.
  - **A drop at each QoS phase:**
    - before PUBACK;
    - before PUBREC;
    - after PUBREL, before PUBCOMP.

    Each runs with a kept and a new session, checking DUP and the same id or a new id, PUBREL resent by coreMQTT, and no loss.
  - **20 queued QoS 1 messages:** at most 16 in flight, all delivered.
  - **A 26 KB payload** sent from its record, with no copy (the pointer coreMQTT is handed lies inside the outbox region).
  - **Expiry:** after 1 h a `QUEUED` message is gone, and a `WAIT_PUBACK` one stays.
  - **A drop in the middle of a PUBLISH,** with messages queued behind it: after reconnecting, a kept session uses the same id with DUP, and a new session a new id. Nothing is lost.
  - **Packet ids across reconnects:** they never restart at 1 while messages wait.
  - **Oversized incoming messages:** a 6 KB PUBLISH at QoS 1 gets its PUBACK, and at QoS 2 its PUBREC, then PUBCOMP on PUBREL. A normal message after it is delivered.

## Bench (`test/bench/mqtt_check.py`)

**Set-up:**

Cases, the ESP32's `test_mqtt.py` plus spec §8's:

   - CONNECTED, with 3.1 and 3.1.1;
   - the derived client ID with an empty one;

7. **`qos`:** the matrix of 2 versions × `cleanSession` 0/1 × 3 phases (cut by the relay).

8. **`retained`:** after a reconnect, the retained message on a subscribed topic reaches the port again.

11. **`tls`:**

    - `tlsVerify` 0 gives CONNECTED;
    - a certificate for another name is rejected;
    - with the clock set, an expired certificate is rejected;
    - the `mqtt` stack headroom after RSA-2048 is at least 1 KB, and `heapMin` with the session up is recorded.
12. **`edge`:**
    - Edge channel 0: a report reaches the report topic, and a 20 KB report passes whole;
    - rw_prot over the request topic gets its reply on the reply topic.

## Bench findings

**Firmware:**
- **The retry wait was cut short by every notify.** `mqtt` waited `retryInterval` in `ulTaskNotifyTake`, and each message queued with `bufferOffline` notifies it, so the gateway dialled again for every serial frame (243 ms apart in `custom`). The wait is now a plain `vTaskDelay` (RED, then GREEN: 3023 and 3024 ms).
- **`/api/status` `stackMin` was blank with Edge's largest model and MQTT on.** About 30 tasks run then (spec §6.1), and `uxTaskGetSystemState` returns 0 for its 24-entry array. The array is now 40 entries, static in AXI (`edge_check memory`: RED, then GREEN).
- **DTCM went over its 120 KB budget** with MQTT's tables in `.bss`. Its topic tables, config, listeners and receive record (16.5 KB) are in AXI; DTCM keeps the stacks (spec §5.3).

**Bench:**
- The relay forwards whole MQTT packets, so a cut falls between packets; `raw=1` carries TLS, `stall` stops in the middle of a packet, `refuse` counts dial attempts.
- **The QoS matrix uses `bufferOffline`.** Without it a frame that comes while the gateway connects again is dropped (spec §8), which is the bench's loss, not the outbox's.
- A relay must start after the restart, so that its first connection (the one it cuts) is the new config's.
- **No report of 20 KB.** Templates are at most 2048 characters, so the largest report is about 3.2 KB (70 `sys_sn` slots), as in 08c. It reaches the report topic whole. The largest model's report buffer is 24 406 B.
- The board here already held an mqtt CA, so `NO CA CERTIFICATE` was not seen; `NO CLIENT CERTIFICATE` (the same check at boot) was. Certificates have no delete; a wiped board shows it.
- The outbox's use is not exposed. The matrix shows its effect: no loss in any of the 12 phases, no QoS 2 duplicate in a kept session.

## Code review round 1 (NOT APPROVED), and the fixes

1. **A message requeued by a new session kept its queue time,** so after more than an hour away it expired before it was sent again. `ob_session(kept, now)` restarts its hour. Found on the way: the requeue also brought back **deleted records** not yet reclaimed (a QoS 0 or acked message behind a slow one), which a new session would have sent again. Only `WAIT_*` records are requeued now. `test_mqtt_outbox` `test_requeue` (RED, then GREEN).
2. **No rest under a broker that never pauses.** Both tasks now rest a tick every 8 turns, and `ms_feed` sends at most 8 messages a call. The bench could not starve anything before the fix: a flood of 182 539 messages through the relay (about 18 000/s) left `serial_hb` (priority 4) at 0.91 heartbeats/s. The `flood` case guards it now.
3. **A mutex not taken in time was released anyway.** `lock()` returns false, and `enqueue` and `mqttgw_add_listener` then refuse. (Round 2 changed what `mqtt` does: see below.)
4. **Packet ids could collide after the counter wrapped,** and a collision dropped the message. New ids skip the ones a waiting message holds (`ob_id_used`), for PUBLISH and SUBSCRIBE. Only `MQTTBadParameter` drops a message; other errors before sending leave it `QUEUED`. `test_id_wrap` (RED, then GREEN).
5. **An unreadable topic list ran as an empty one.** `store_get` gives a known name's default, so NULL is no memory: MQTT stays off with `NO MEMORY` (the `mqtt` config too). Not testable on the bench; read in the code.
6. **The mid-PUBLISH test did not fail a send.** The scripted broker now reads 2000 bytes of the 20 KB PUBLISH and closes. The test asserts `MQTTSendFailed` and the id kept, then the resend in both sessions. A mutation (dropping the message on `MQTTSendFailed`) fails it.
