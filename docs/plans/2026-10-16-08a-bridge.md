# Plan 08a: the per-port network bridge (no TLS)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** UART1 and UART2 each have their own network bridge, with the ESP32's working modes:
- UDP client, TCP client, UDP server, TCP server, HTTP client;
- the extra socket modes (Modbus TCP gateway, short connection, both, multicast);
- polling, registration, the network heartbeat;
- the IO slave on both ports;
- `bufferOffline` and `idleRestart`.

Verified on the board with the looped RS485 ports, against peers on the bench PC.

**Spec:**
- §6.1: task `bridge[n]`, prio 8, 6 KB; `idle`, prio 2, 2 KB.
- §6.3: `services` after `serial`, before `webapi`.
- §6.4: per-port rules; the IO slave on both ports.
- §5.3: SRAM2+3 for the serial → network rings and `bufferOffline`.
- §5.6: lwIP; `ENOMEM`/`ENOBUFS` mean "retry".
- §4 table: `services/bridge.c` "one instance per port, no RFC 2217, no PUSR"; `net.c`.
- §13: differences from the ESP32.

**Roadmap:** row 08 is split three ways:
- **08a, this plan:** the bridge without TLS;
- **08b:** mbedTLS 3.6 LTS, `tlsconn.c` (§7.3), TLS on the TCP client and HTTPS, the certificate check on upload (F20);
- **08c:** `edge_rt` per bus, Modbus TCP devices, the report buffer of at most 26 KB (§9.4), and Edge's remote access through the bridge.

## Rules that apply

- **Configs are read once at boot:** `port1`, `port2`, `system`, `io`. A change applies after a restart.
- Keep it simple, and run only the affected tests. Codex reviews before the PR.
- **The ESP32 `bridge.c`, `net.c` and `services.c` are the behavioural baseline,** per port:
  - one bridge task per port, which runs the selected mode;
  - the serial subscriber only queues frames, never touches the network (§6.4 rule 3);
  - a frame without a peer is dropped, unless `bufferOffline` keeps it or it is what opens a short connection;
  - heartbeats only fill silences;
  - the Modbus TCP gateway answers the IO slave address from the IO map, never from the bus;
  - with `modbusException`, a silent slave gets exception 0x0B;
  - polling sends the answer only to the asking client;
  - the TCP server keeps up to `maxClients` (≤ 16) clients, with `clientLimitAction` 0 (drop the oldest) or 1 (refuse the new one), and `allowedClients`;
  - UDP server replies go to the last sender; UDP client accepts only its peer (or any port with `udpAnyRemotePort`);
  - HTTP client: one request per serial frame, HTTP/1.0, GET with the data in the URL or POST with it as the body, `httpStripHeaders`.
- **Gone** (STM32 scope): RFC 2217 and the PUSR baud sync, which also removes `serial_set_line` and `serial_purge`.

## Architecture

### `components/services/bridge_core.{h,c}`

Pure C, host-tested (`test_bridge_core`):
- **`bridge_cfg_parse(port_json, system_json, &cfg)`:** the fields of `port<n>` and `bufferOffline` of `system`, plus the derived flags `modbus_gw`, `modbus_client`, `short_conn` (as the ESP32's helpers).
- **`mbtcp_acc_t`:** the Modbus TCP reassembly per connection.
  - `mbtcp_push(acc, data, len, cb, ctx)` calls `cb` with each whole ADU (`mb_tcp_frame_len`).
  - A request split over segments is joined; several in one segment are each delivered; a non-Modbus prefix resynchronises.
- **`http_head(cfg, data, len, out, max)`:** the request head; the header lines are normalised to CRLF.
- **`http_body(resp, len, strip, &off)`:** the body with or without the headers.
- **`bridge_registration(cfg, out, max)` and `bridge_heartbeat(cfg, out, max)`:** from `sysmgr_payload()` (below).
- **`tx_progress(conn, frame, len, send_fn, ctx, now_ms)`:** the non-blocking send of one frame to one connection (§5.6, Codex r1). It returns `TX_DONE`, `TX_PENDING` or `TX_LOST`.
  - `send_fn` returns the bytes taken, `NET_AGAIN` or `NET_FAIL`.
    - `net_classify(errno)` maps `EWOULDBLOCK`, `EAGAIN`, `ENOMEM` and `ENOBUFS` to `NET_AGAIN`, anything else to `NET_FAIL`.
    - They cannot be told apart: for a non-blocking write, lwIP itself turns `tcp_write`'s `ERR_MEM` into `ERR_WOULDBLOCK` (`api_msg.c`, Codex r3).
  - The connection keeps its offset into the frame, so a partial send then `NET_AGAIN` loses and repeats no byte. `NET_AGAIN` by itself never closes and never drops.
  - **`TX_LOST`** comes on `NET_FAIL`, or after `TX_STALL_MS` (10 s) with no byte taken, whatever the temporary cause (a full window, or lwIP short of memory).
    - This "no progress" rule is **a deliberate exception to §5.6** for TCP. Without it, one stuck connection would hold its port's other clients forever; the ESP32 dropped one after its 5 s send timeout.
    - §5.6 gets the same sentence when this plan is approved.
- **`accept_allowed(netconn_free, reserve)`:** the §5.6 gate. A TCP server's listener accepts only while at least `reserve` (4) netconns are free.

### `components/sysmgr`: `sysmgr_payload(content, custom, hex, out, max)`

The ESP32's `sys_payload`: 0 custom, 1 IMEI, 2 serial number, 3 ICCID, 4 MAC.
- `serial.c`'s heartbeat moves to it, so the code exists once.
- IMEI and ICCID are empty until Plan 10.
- The custom text uses `sf_payload_custom` (host-tested in 07a).

### `components/iomgr/io_mb.c`

The ESP32's IO slave: the Modbus map and `iomgr_remote()`, moved from 07b (ruling 4 there):
- coils 0.. = DO (FC 1, 5, 15);
- discrete inputs 0.. = DI (FC 2);
- input registers 0.. = AI as float32 ABCD in mA (FC 4), with exception 4 when the AI failed.

It reads through a small table of getters (`io_mb_ops_t`), so `test_io_mb` runs it against fakes. On the board the getters are `iomgr_do_get`, `iomgr_do_set`, `iomgr_di_get`, `iomgr_ai_ua` and `iomgr_ai_ok`.

### `components/services/net.c`

The ESP32's file, almost unchanged, on lwIP sockets: `net_resolve`, `net_tcp_connect` (with timeout and a local port), `conn_send`, `conn_recv`, `conn_close`.
- `conn_t` keeps its `tls` pointer, always NULL in 08a, for 08b.
- **Sends are non-blocking** (`MSG_DONTWAIT`, no `SO_SNDTIMEO`). `conn_send_some` maps `EWOULDBLOCK`, `EAGAIN`, `ENOMEM` and `ENOBUFS` to `NET_AGAIN` and anything else to `NET_FAIL` (§5.6).
- **lwIP's own names, everywhere** (Codex r1): with `LWIP_POSIX_SOCKETS_IO_NAMES` 0, `close()` and `fcntl()` are newlib's, not lwIP's. So the code calls `closesocket()` (`lwip_close`) and `lwip_fcntl()`, on the error paths as on the normal ones. `check_elf.py` gates that `app.elf` links no `close`, `_close`, `fcntl` or `_fcntl`.

### `components/services/bridge.c`

The ESP32's file made one instance per port (`bridge_t s_br[2]`, `bridge_start(port)`):
- **The serial → network queue** is a FreeRTOS MessageBuffer per port (frames kept whole), with storage in `.sram23_bss`:
  - 8 KB, or 32 KB with `bufferOffline`; static 2 × 32 KB, within the 80 KB §5.3 gives the rings and `bufferOffline`;
  - one writer (the subscriber on `serial_rx[n]`) and one reader (`bridge[n]`).
- **Sending, per port:** the bridge takes the next frame from the MessageBuffer only when every connection has sent the current one (`tx_progress` per connection, its own offset) or was lost.
  - Meanwhile the frames wait in the MessageBuffer; the ones that do not fit are dropped and counted by the subscriber, and `serial_rx[n]` is never blocked.
  - **The work per pass is bounded** (Codex r2):
    - at most 8 frames out and 8 reads in (4 KB each way);
    - a pass that did any work, a failed send attempt included, ends with `vTaskDelay(1)`;
    - an idle pass blocks in `select()` (readability, and writability for the connections with a frame in flight), at most 10 ms.

    So `bridge[n]` (prio 8) gives way at least once a tick under any load, and `io` (prio 6) and the rest are never starved. At 4 KB a tick each way, that is about 4 MB/s, far above a serial port's 23 KB/s.
- **UDP:** a `sendto` that returns `NET_AGAIN` keeps the datagram for the next pass, however long (UDP has no connection to lose); meanwhile new frames wait in the MessageBuffer. A datagram is never sent in part.
- **Accepting:** the TCP server's listener is in the `select()` set only while `accept_allowed()`; pending connections wait in the backlog.
  - Bench console `Y<n>` sets the reserve (default 4), so the bench can see the gate with a few clients.
- **Data from the network** goes to `serial_write(port, …)` or, for the Modbus gateway and polling, to `serial_transact(port, …)`, which only ever touches bus n (§6.4).
- **The IO slave address** is answered by `iomgr_remote()` on both ports.
- **Tasks:** `bridge1` and `bridge2`, prio 8, 6 KB each, static stacks in AXI. §5.3's AXI line is updated with them (Codex r1): about 12 KB, within the about 37 KB left there.
- **TLS:** with `tls` ≠ 0, the port's bridge does not start, logs "TLS comes with Plan 08b", and its state reads `TLS UNAVAILABLE`.
- **Status:** `bridge_status(port, &st)` gives the state (`LISTEN`, `CONNECTED(n)`, `CONNECTING`, `WAITING`, `ERROR`).

### `components/services/services.c`

- **`services_start(sys)`:** both bridges, and the `idle` task when `idleRestart` > 0.
- **`svc_net_activity()`:** data moved to or from the network; heartbeats do not count.
- The `idle` task restarts through `sysmgr_restart_later(500)` after `idleRestart` s without activity.
- **`/api/status`:** `ports[n].state` comes from `bridge_status` (no longer `NOT STARTED`).
- **Init order (§6.3):** `services_start` runs in `app_main` after `serial_start` and before `webapi_start`. `bench_serial` keeps subscribing to both ports; on the bench the bridge and the bench peer are on different ports.

### Bench console

`F<port>` also prints the hex of the last frame (at most 64 bytes), so the bench can check content, not only lengths.

## Review Focus

1. **A TCP client that stops reading:** that port's other clients wait for it, and after 10 s without a byte taken it is dropped (`TX_STALL_MS`). The other port is not affected. `test_bridge_core` pins the timing; the bench has a client that never reads while another one keeps receiving after the drop.
2. **Modbus TCP segmentation and pipelining:** pinned by `test_bridge_core` (split, two in one, garbage before a frame).
3. **The serial side faster than the network** (a 230 400 stream into a slow TCP peer): frames beyond the queue are dropped and counted, never blocking `serial_rx[n]`; checked with a 1 s burst on the bench.
4. **The peer's address changes** (DNS): resolved again at each connect (TCP) or every 5 s while unresolved (UDP), as on the ESP32.
5. **`idleRestart` with only heartbeats flowing:** they do not count as activity (the bench case 8 keeps the network heartbeat on).

## Bench findings

- **N1. lwIP and its callers did not share `errno`.**
  - `app/arch/cc.h` defined `LWIP_PROVIDE_ERRNO 0`, and lwIP tests that name with `#ifdef`. So lwIP used its own errno codes and newlib's global errno, while the bridges and Mongoose read newlib's per-task `__errno()`, which was always 0.
  - The TCP client's non-blocking connect looked failed: the PC saw the connection, the board closed it.
  - The define is gone. lwIP, `net.c` and Mongoose now all use `__errno()`; `web_check` passes 44 of 44 on it.
- **N2. Both ports' factory configs listened on 23,** so UART2's TCP server could not start. `port2` defaults to 24 (`test_cfgmodel`); `check_schema.py` stays consistent. Stored configs keep their value.
- **N3. The bridges' state and buffers (about 24 KB) went to SRAM2+3:** in DTCM they broke its 120 KB budget, and AXI was at 90 %. §5.3 is updated.
- **N4. The Windows firewall blocked Python inbound;** the user allowed it, so the bench peers run there (ruling 4).
- **N5. `idleRestart` takes 0 or 60–65535 s** (the config's rule); the bench uses 60 s, not 30 s.
- **N6. A client that never reads,** with WSL's kernel buffers on the PC side, was dropped after 11.6 s. The other client lost what streamed meanwhile (frames dropped and counted, `mem.uart[n].bridgeDropped`), then got everything at the full rate. This is the designed behaviour (§5.6 exception).
- **N7. The RS485 loop is half duplex:** the load case only reads on the PC, and loads the network with a UDP flood instead.
- **N8. A board that ran an older build of this project** showed FlashDB CRC errors on `system` (Plan 06b B4 again). `Z WIPE` cleaned it; its defaults are then 23/24.

## Codex round 1 (NOT APPROVED), and the fixes

1. **Sends on a memory shortage** were both "retried" and "closed after 5 s". Now sends are non-blocking, with an offset per connection (`tx_progress`, host-tested): `EWOULDBLOCK`, `EAGAIN`, `ENOMEM` and `ENOBUFS` keep the data and the socket. Only a peer that takes no byte for 10 s is lost.
2. **`close()` and `fcntl()` are not lwIP's** with `LWIP_POSIX_SOCKETS_IO_NAMES` 0: `closesocket()` and `lwip_fcntl()` are used everywhere, and `check_elf.py` gates that no `close`/`fcntl` is linked.
3. **The §5.6 accept gate** (fewer than 4 free netconns: no `accept`) is added (`accept_allowed`, host-tested; bench with a raised reserve).

The stacks of `bridge[n]` go into §5.3's AXI line.

## Codex round 2 (NOT APPROVED), and the fixes

1. **A memory shortage could still close a socket after 10 s.** (Superseded in round 3.) `NET_NOMEM` (`ENOMEM`, `ENOBUFS`) and `NET_FULL` (`EWOULDBLOCK`, `EAGAIN`) are now told apart. A shortage never closes or drops, however long it lasts. Only 10 s of a full window with no byte taken loses a peer, written as a deliberate exception to §5.6. Tested with 60 s of `NET_NOMEM`.
2. **`select()` alone did not guarantee a yield.** The work per pass is bounded (8 frames and 8 reads, 4 KB each way), and a busy pass ends with `vTaskDelay(1)`. The new bench case 9 checks that the `io` task keeps its pace under a continuous load.

## Codex round 3 (NOT APPROVED), and the fix

1. **`EWOULDBLOCK` does not prove a full window:** lwIP reports its own memory shortage on a non-blocking write as `ERR_WOULDBLOCK`. So the classes are one again (`NET_AGAIN`), and the 10 s rule is stated as a "no progress" policy, whatever the temporary cause: a deliberate exception to §5.6 for TCP. `NET_AGAIN` alone never closes; `net_classify` is tested against lwIP's errno values. A failed send attempt counts as work, so the pass yields.
