# Plan 04b: OTA and anti-clone on the board

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The bootloader runs the anti-clone check of Plan 04c and the install logic of Plan 04a on the real flash, and the app checks its binding and takes a new image over UART7. All of it is proven on the bench board.

**Architecture:**
- **Bootloader** (`boot/boot.c`), in this order:
  1. watchdogs, safe outputs and clocks;
  2. QSPI in indirect mode (`qf_nor_t`), then SPI4 (`spi_nor_t`);
  3. `bind_check()`; on any failure, halt with no Reload;
  4. Reload sampled for 5 s;
  5. `install_run()`;
  6. QSPI in memory-mapped mode, then the jump.

  On `INSTALL_HALT` it blinks fast and polls Reload; Reload held 5 s restores the factory image. The bootloader never leaves memory-mapped mode once it has entered it.
- **Drivers:** `components/board/spi_nor.c` (SPI4, shared with the app) and `boot/qspi_flash.c` (`qf_nor_t`). Both implement `nor_t` with 03h/EBh read, 20h erase and 02h program, with deadlines of twice the datasheet maxima.
- **App** (`app/bench_ota.c`):
  - `app_bind_ok()` before anything starts;
  - console `o` reports the three images;
  - console `u` streams an image into staging with `ota_stage_*`, then resets.
- **Build:**
  - `APP_VERSION` is set once in CMake;
  - `mkimage.py` writes `app.img` after every app build, and `flash.sh` flashes `app.img`;
  - SPI4 is in `boot.ioc` (generated by `mkioc.py`), and `MX_SPI4_Init` is called in both images.
- **Bench:**
  - `board.upload()` sends 4 KB blocks, each after an acknowledgement;
  - `ota_check.py` covers 30 checks: install, resets mid-install, an upload cut off, SPI4 init failing, Reload restore at power-up and from the halt loop, clone erase read back over SWD, an app refusing a record, re-provisioning.

**Tech Stack:** STM32H750 HAL (QSPI, SPI), CubeMX headless, CMake, Python 3, PowerShell serial I/O, OpenOCD (Reload simulation), STM32CubeProgrammer.

**Spec:** `stm32/docs/specs/2026-10-14-stm32-firmware-design.md` §6.2 (SPI4 in the bootloader, memory-mapped mode only at the jump), §11.2 (LED during the Reload wait), §11.3, §11.5, §12.4 (production order, the team loader). **Roadmap:** row 04b.

## How this plan was made

The code was written and run on the bench board before this document, the same way as Plan 02. The tasks below record what was done, in order, with what each step showed. Bench findings that changed the code or the spec are marked **B**.

## Bench findings

- **B1. SPI4 reads time out in the app now and then.** One report read staging as `IMG_EREAD` after about 94 ms, which is the 100 ms HAL timeout. A master receiving in simplex mode clocks on by itself, so a task switch in the middle of a read overruns the RX FIFO. Fix: `MasterReceiverAutoSusp` enabled in `mkioc.py`. Afterwards, 28 reports over 5 boots showed no error, and the OTA runs wrote and read hundreds of kilobytes in the app with the wdog task running.
- **B2. The CubeMX SPI4 defaults are 4-bit frames at 60 MHz.** `mkioc.py` now sets 8-bit, mode 0, prescaler 4 (30 MHz) and keeps the IO state.
- **B3. A reworked board must be bound before it is flashed.** `flash.sh` resets the board after flashing. A board still carrying the record of another UID booted, found a "clone", and erased the application that had just been flashed. The production order in §12.4 is now: bind first, then flash. That order is safe on a fresh chip too, since binding needs no bootloader.
- **B4. Plan 02's hostile check expected an erased header.** The image now has a real header, magic `SBIO` = `4f494253`. Every failure also left the flash in continuous-read mode, so the next run read garbage and passed by accident. The check now expects the magic, and all six runs read `4f494253`.
- **B5. `NOR_TIMEOUT` clashes with a macro in `stm32_hal_legacy.h`.** It is renamed `NOR_ETIMEOUT`, to sit with `NOR_EIO`.
- **B6. Timings on the board:**
  - binding check plus the image checks at boot: about 30 ms;
  - a 44 KB install: 0.56 s;
  - a 300 KB install: 3.7 s;
  - upload at 115200 baud: 44 KB in 4.3 s, 300 KB in 30 s.
- **B7. Sizes:**
  - bootloader 34.9 KB of the 64 KB budget (Monocypher about 11 KB);
  - app 44.7 KB;
  - worst stack chain in the bootloader about 2 KB, measured with `-fstack-usage`, against the 4 KB reserved.

## Codex round 1 (NOT APPROVED), and the fixes

1. **A SPI4 that failed its init was still used.** If the JEDEC read failed once but the bus worked afterwards, the bootloader could still install or seed, against ruling 3. Fix: `boot.c` hands `install_run` a `nor_t` whose every operation fails.
   - Bench case: `spi_nor_init()` is forced to return `NOR_EIO` through the debugger, with a new image in staging and the bus fine. The log shows `spi4 id ... FAILED`, nothing is installed and the app runs. The next normal boot installs.
2. **WIP = 0 does not prove an erase.** GD25Q32E ignores an erase of a protected sector (§7.15). The Reload path's staging erase is now read back: the magic must read erased before QSPI is touched, else halt with `WHY_STAGING`.
   - Host: the simulator gained `SIM_ERASE_SILENT`, and the new `test_install` case was RED, then GREEN.
   - Mutants: "staging erase not verified" added, 25 of 25 caught.
   - The copies were already safe, because the read-back before the magic catches a destination that was not erased.
3. **Board cases Codex asked for, all added to `ota_check.py`:**
   - an upload cut off after 8 KB: nothing installed;
   - Reload from the halt loop (QSPI blanked);
   - the clone erase read back over SWD (`board.qspi_read32`): the slot reads erased;
   - an app built with another public key refuses the record while the bootloader passes.
4. **The physical SW1 is still to be checked by the user** (ruling 6).

While adding these, the reset-mid-install case turned out to be timed from PowerShell opening the port, so on a slow start the install had already finished. The image is now staged with `U` (no reset), the bench's own first reset starts the install, and the case requires at least 3 installs to be cut short. The run gave 5 cut, then one completed.

## Rulings (for review)

1. **LED WORK blinks slowly during the Reload wait** (500 ms toggles) instead of staying on. LED WORK and WDI share PC10, and a steady LED would stop the SGM706 kicks. The halt blinks fast (100 ms). The spec now says so (§11.2). Cost if wrong: only the visible signal changes.
2. **A failed binding check, or a failed QSPI init, halts without polling Reload.** §11.5 says Reload cannot rescue a clone. A QSPI that cannot be initialised cannot be restored either. Cost if wrong: a board whose QSPI fails at init needs SWD, as before.
3. **SPI4 failing at boot is not fatal, and it is not used.** A stand-in `nor_t` whose operations all fail takes its place, so nothing is installed, seeded or restored, and a valid QSPI image still runs. Cost if wrong: a broken SPI4 goes unnoticed until an OTA fails. The boot log prints `spi4 id ... FAILED`.
4. **The bootloader never leaves memory-mapped mode.** All QSPI work happens in indirect mode before memory-mapped mode is entered, so the ES0392 §2.7.4 sequence "on leaving memory-mapped mode" is never needed. Cost if wrong: none found. The Plan 02 hostile resets, which do leave memory-mapped mode through the debugger, still pass.
5. **The team loader stays, and our own loader is deferred** until R20 is fitted. The team loader already flashes images and binding records. Its only flaw is that it does not kick WDI, which matters only with R20. Cost if wrong: one more plan item when R20 is fitted.
6. **Bench Reload is simulated through the debugger:** a hardware breakpoint at `boot_main`, then PA8 driven low, so R136 limits the current to about 0.3 mA. The physical button was not pressed. **The user should check the real SW1 once.**
7. **One version number:** `APP_VERSION` 0.4.0 in CMake, compiled in and written into the header. `BOOT_VERSION` is 0.4.0.

## Review Focus

1. **The order at boot:** binding first, then Reload, then install. A clone must never reach Reload or the install. Pinned by `ota_check` case 5.
2. **A reset at any point of an install:** the next boot installs again and ends on the new image, never halted. Pinned by `ota_check` case 3: 5 random resets during a 3.7 s install. The host matrices of Plan 04a cover every operation.
3. **SPI4 reads interrupted by the RTOS** (B1). Pinned by the repeated reports, and by the uploads, which read staging back while the wdog task runs.
4. **The watchdog during long flash work:**
   - every wait inside the drivers kicks;
   - an install of 300 KB with resets never tripped IWDG1;
   - the Plan 02 IWDG1 resets still come about 1.5 s after the last kick.
5. **Regression of Plan 02:** pin reset, 10 software resets, 3 IWDG1 resets, XIP CRC of `app.img`, the hostile continuous-read and erase resets. All pass (`boot_check.py`, with and without `--hostile`).
